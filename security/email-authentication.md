# メールのセキュリティ — SPF / DKIM / DMARC で自動返信を届ける

## なぜ自動返信が Gmail に届かないのか

- 問い合わせフォームからの自動返信が、Gmail で迷惑メール扱いになる・届かないことがある
- 原因の多くは「なりすまし対策」に弾かれていること
  - From ドメインと、実際に送信しているサーバが一致していない
  - 認証情報（DNS レコード）が未設定、または不足している
- Gmail をはじめ主要メールサービスは、未認証メールを厳しく扱う方向に進んでいる
- 対策の中心が **SPF** / **DKIM** / **DMARC** の3つ
- 本記事では、問い合わせフォームの自動返信を届ける視点で3つの役割を整理する

## メール認証の全体像

- 3つは別々の仕組みだが、組み合わせて初めて受信側が信頼しやすくなる

| 仕組み | 何を検証するか | 設定場所のイメージ |
|---|---|---|
| **SPF** | そのドメインから送ってよいサーバか | DNS の TXT レコード |
| **DKIM** | メールが改ざんされていないか・正当な送信者か | DNS の TXT + 送信側の署名 |
| **DMARC** | SPF / DKIM の結果をどう扱うか（拒否・隔離など） | DNS の TXT レコード |

- よくある誤解: 「サーバの SMTP 設定だけ直せば届く」
- 実際は DNS 側の認証設定が欠けていると、Gmail 側で評価が下がる
- レンタルサーバやトランザクションメールサービスを使う場合も、ドメイン側で SPF / DKIM / DMARC を揃えるのが基本

## SPF（Sender Policy Framework）

- SPF は「このドメインのメールを送ってよい IP / サービス」を DNS で宣言する仕組み
- 受信側は、実際の送信元 IP が SPF レコードに含まれるかを確認する
- 問い合わせフォームの自動返信では、次のどちらか（または両方）が送信元になりやすい
  - レンタルサーバのメール機能
  - SendGrid / Amazon SES などの外部送信サービス
- レコードはドメインの TXT として公開する — 例:

```text
; 例：レンタルサーバの SPF を許可する（値は契約サービスに合わせる）
v=spf1 include:example-host.jp ~all
```

```text
; 例：外部送信サービスも使う場合（include を追加する）
v=spf1 include:example-host.jp include:sendgrid.net ~all
```

- `~all` は「一覧外は弱い失敗」、`-all` は「一覧外は失敗」として扱う意図
- 最初は `~all` で様子を見て、送信経路を洗い出してから厳しくするのが無難
- SPF レコードは原則 **1つ** — 複数置くと検証が破綻しやすい

> 参照: [RFC 7208 — SPF](https://datatracker.ietf.org/doc/html/rfc7208)

## DKIM（DomainKeys Identified Mail）

- DKIM は、送信時にメールへ電子署名を付け、受信側が公開鍵で検証する仕組み
- 「途中で改ざんされていないか」「宣言どおりのドメインから来たか」を確認できる
- 設定の流れは次のとおり
  1. 送信サービスまたはサーバ側で DKIM を有効化する
  2. 発行された公開鍵を、DNS の TXT（セレクタ名付き）に登録する
  3. 実際の送信メールに DKIM 署名が付いているかを確認する
- DNS 名のイメージは `selector._domainkey.example.com`
- SPF だけでは不十分なケースがある — 転送や途中経路の影響を受けやすいため、DKIM とセットで入れるのが実務的
- レンタルサーバのコントロールパネルに「DKIM を有効にする」がある場合は、そこから公開鍵を取得して DNS に貼る

> 参照: [RFC 6376 — DKIM](https://datatracker.ietf.org/doc/html/rfc6376)

## DMARC（Domain-based Message Authentication, Reporting and Conformance）

- DMARC は、SPF / DKIM の検証結果を受けて「不合格メールをどう扱うか」を宣言する仕組み
- あわせて、認証失敗のレポートを受け取るメールアドレスも指定できる
- レコード例:

```text
; 例：まずは監視から始める（不合格でも配信は拒まない）
v=DMARC1; p=none; rua=mailto:dmarc-report@example.com; adkim=r; aspf=r
```

```text
; 例：運用が安定したら隔離へ（迷惑メール扱いを指示）
v=DMARC1; p=quarantine; rua=mailto:dmarc-report@example.com; adkim=r; aspf=r
```

- `p=` の代表値
  - `none` — 監視のみ
  - `quarantine` — 隔離（迷惑メール扱いを推奨）
  - `reject` — 拒否
- いきなり `reject` にすると、正規の自動返信まで落ちることがある
- 推奨手順: `none` でレポートを見る → 送信経路を直す → `quarantine` / `reject` へ段階的に厳しくする
- DMARC が効く前提として、SPF と DKIM の少なくとも一方（実務では両方）が通っている必要がある

> 参照: [RFC 7489 — DMARC](https://datatracker.ietf.org/doc/html/rfc7489)

## 設定の進め方とよくある間違い

### 進め方

1. 自動返信の **実際の送信元** を確認する — レンタルサーバか、外部サービスか
2. 送信元に合わせて SPF の `include` / IP を書く
3. 同じ送信経路で DKIM を有効化し、公開鍵を DNS に登録する
4. DMARC を `p=none` で入れ、レポートと Gmail の到達を確認する
5. 問題が落ち着いたら `quarantine` 以上へ上げる

### よくある間違い

### 1. From アドレスのドメインと認証ドメインが食い違う

- `From: info@example.com` なのに、別ドメインのサーバから無認証で送っている
- ドメイン所有者としての認証が取れず、Gmail で不利になる

### 2. SPF レコードを複数置いている

- TXT が複数あると、どれを正とするか受信側の解釈が崩れる
- `include` で1本にまとめる

### 3. 外部送信サービスを追加したのに SPF / DKIM を更新していない

- フォームプラグインや SMTP プラグインで送信経路だけ変えると起きやすい
- 経路を変えたら DNS も必ず見直す

## まとめ

- 問い合わせフォームの自動返信が Gmail に届かない主因は、メール認証不足であることが多い
- **SPF** で送信してよいサーバを宣言する
- **DKIM** で改ざん検知と送信元の正当性を補強する
- **DMARC** で不合格時の扱いとレポート受信を宣言する
- 3つはセットで入れる — どれか1つだけでは不十分なことが多い
- 導入は `DMARC p=none` から始め、送信経路を固めてから厳しくする
- From ドメイン・送信サービス・DNS レコードの三者を一致させるのが到達率改善の要点

# Web制作会社のコーディングガイドライン — 参考資料と目次案

調査日：2026-10-13

## 作成の背景と対象

テスト環境にBasic認証が設定されておらず、制作途中のサイトが外部から閲覧可能になり、検索エンジンのクローラーに巡回・インデックス登録されるインシデントが発生した。

この再発防止と制作品質の統一を目的として、経験3年未満のジュニアクラスのフロントエンドエンジニア向けに社内ガイドラインを作成する。対象は、静的サイト（HTML・CSS・バニラJavaScript）とWordPressによるサイト制作。

コーディングの記法に加え、環境構築・検証・公開作業までを対象とする。以下の目次は、公開資料を参考に当社の対象技術と今回のインシデントに合わせて組み立てた提案であり、業界共通の規格ではない。

## 今回のインシデントを踏まえた重点方針

以下は当社で採用することを提案する運用方針。

- **テスト環境は、制作物をアップロードする前にアクセス制限を設定する。** HTTPS上のBasic認証を標準とし、案件に応じてIP制限やVPNなどを責任者が選定する。Basic認証は認証情報自体を暗号化しないため、HTTPSと組み合わせる。[MDN：HTTP authentication](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Authentication)
- **アクセス制限と検索エンジン対策を分けて確認する。** 非公開コンテンツは認証で保護する。`noindex`は検索結果への掲載を制御する指定であり、URLを知っている人の閲覧を防ぐものではない。[Google：共有するコンテンツを制限する](https://developers.google.com/search/docs/crawling-indexing/control-what-you-share?hl=ja)
- **テスト環境の`noindex`は補助策として環境別に設定する。** HTMLのmetaタグ、またはPDFなどにも適用できる`X-Robots-Tag`を使う。ただし、認証や`robots.txt`でアクセスを遮断している間、クローラーはページの`noindex`を読めない。既存の検索結果がこれだけで直ちに消えるとは考えない。[Google：noindexによる除外](https://developers.google.com/search/docs/crawling-indexing/block-indexing?hl=ja)
- **`robots.txt`だけで非公開を実現しない。** ページをクロール禁止にしても、外部リンクなどからURLが検索結果に残る場合がある。Googleは`robots.txt`内の`noindex`指定をサポートしていない。[Google：noindexによる除外](https://developers.google.com/search/docs/crawling-indexing/block-indexing?hl=ja)
- **WordPressの「検索エンジンがサイトをインデックスしないようにする」だけに頼らない。** この設定は閲覧を制限しない。テスト環境には別途アクセス制限を設定し、設定画面と実際の出力を確認する。[WordPress：Settings Reading screen](https://wordpress.org/documentation/article/settings-reading-screen/)
- **誤公開時はアクセス遮断を優先し、検索結果の削除を並行して進める。** Search Consoleの削除ツールはGoogle検索での一時的な非表示であり、サイトの非公開化や恒久的な削除の代わりにはならない。未公開コンテンツを`noindex`の読み取り目的で再公開しない。[Google：Removals tool](https://support.google.com/webmasters/answer/9689846?hl=en)

## 最初に整備するチェックリスト案：テスト環境のURL共有前

設定した担当者とは別の確認者がチェックし、確認日時・対象URL・結果を記録する。満たせない項目がある場合は、共有前に責任者へ相談する。

- [ ] 接続先がテスト環境であり、本番環境ではないことを確認した。
- [ ] HTTPSでアクセスでき、認証情報をHTTPで送信しない構成になっている。
- [ ] サイト全体にBasic認証等のアクセス制限を設定した。
- [ ] 認証情報を付けないGETリクエストで、制作中の内容が返らないことを確認した。Basic認証なら原則401と`WWW-Authenticate`を確認する。
- [ ] 誤った認証情報では拒否され、正しい認証情報でのみ閲覧できる。
- [ ] トップ、下層、画像・PDFの直リンク、WordPressのuploads・REST API・フィード等も保護されている。
- [ ] 存在する別ホスト名・HTTP経由・CDN経由でも、保護を迂回して閲覧できない。
- [ ] 認証済みのキャッシュが未認証ユーザーへ配信されないことを確認した。
- [ ] 補助策としてnoindexの出力を確認した。WordPressでは表示設定に加え、実際のHTML／レスポンスも確認した。
- [ ] テスト用フォームが顧客・一般ユーザーへ誤送信しない設定になっている。
- [ ] 認証情報の共有先を限定し、Gitや公開ファイルに認証情報を含めていない。
- [ ] 別担当者による確認が完了し、確認記録を残した。

未認証の確認には、認証済みブラウザをそのまま使わず、認証情報を送らないHTTPクライアント等を使う。Basic認証の401応答とHTTPSの根拠は[MDNのHTTP認証の説明](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Authentication)を参照。

## 本文を作成するときの書き方

ジュニアが迷わず実行できるよう、各ルールは「必須／推奨」「適用対象」「理由」「具体的な手順・コード例」「確認方法と合格条件」「相談先」の順で記述する。特にアクセス制限は、設定画面のスクリーンショットだけで完了とせず、外部からの未認証リクエストの結果を合格条件に含める。

初版は第2章・第14章・第15章とチェックシートを先に具体化し、その後に言語別の規約を整備する。フォーマッターで機械的に統一できる記法は設定に任せ、レビューではアクセス制限、操作性、変更の影響範囲などを重点的に確認する。

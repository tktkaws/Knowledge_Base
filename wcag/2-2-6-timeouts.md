# 2.2.6 タイムアウト（AAA）

## 達成基準の概要

- WCAG 2.2 達成基準 2.2.6「タイムアウト」（Timeouts）
- レベル **AAA**（最高の適合レベル）
- 原則2「操作可能（Operable）」> ガイドライン 2.2「十分な時間」に属する
- **ユーザーの無操作**がデータ損失につながる場合、その無操作の**継続時間を事前に告知**すること
- 例外：ユーザーが何も操作しなくても**20時間超**データを保持する場合

> **参照**
> - [WCAG 2.2 — Success Criterion 2.2.6 Timeouts](https://www.w3.org/TR/WCAG22/#timeouts)
> - [Understanding SC 2.2.6 Timeouts](https://www.w3.org/WAI/WCAG22/Understanding/timeouts.html)

## 達成基準の原文（要約）

- データ損失を引き起こしうる**ユーザー無操作の継続時間**について、ユーザーに警告すること
- ただし、ユーザーが何も操作しなくても**20時間超**データが保持される場合は除く

> **参照**
> - [WCAG 2.2 — Success Criterion 2.2.6](https://www.w3.org/TR/WCAG22/#timeouts)

## ユーザー無操作とは

- **ユーザー操作が一切発生しない連続した期間**
- 追跡方法はサイト／アプリケーションが決定する
- 例：マウス移動・キー入力・タップ・フォーム入力などがない状態
- セッションタイムアウトの多くは、この無操作期間を基準にする

```text
無操作の例：
  フォーム入力後、15分間キーやマウスを動かさない
  ログイン後、30分間ページを操作しない

無操作ではない例：
  読み上げソフトで長文を聴いている間の操作なし（実装次第）
  別タブで作業している間の操作なし（実装次第）
```

> **参照**
> - [Understanding SC 2.2.6 — Key Terms: user inactivity](https://www.w3.org/WAI/WCAG22/Understanding/timeouts.html#dfn-user-inactivity)

## なぜ必要か

- 認知障害のあるユーザーは、読解・入力・判断に長い時間がかかることがある
- 言語関連・記憶関連・注意関連の障害があるユーザーは、途中で休憩が必要
- 実行機能に影響のある障害があるユーザーは、一気に手続きを終えられない
- タイムアウトの存在を知らないと、休憩後に戻ってデータが消えている
- 事前告知があれば、休憩の可否や準備の要否を判断できる

> **参照**
> - [Understanding SC 2.2.6 — Benefits](https://www.w3.org/WAI/WCAG22/Understanding/timeouts.html#benefits)

## 適合の3つの経路

| 経路 | 内容 | 例 |
|---|---|---|
| 20時間超のデータ保持 | 無操作でも20時間超データを残す | 下書きをサーバーに24時間保存 |
| 20時間超のセッション | 無操作タイムアウトを20時間以上に設定 | セッション有効期限を24時間 |
| プロセス開始時の告知 | 無操作で切れるまでの時間を最初に伝える | 「1時間操作がないとセッションが切れます」 |

- **最も望ましいのは20時間超のデータ保持**
- 障害のあるユーザーと高齢者が、休憩を挟んで作業を完了しやすくなる
- データ保存が現実的でない場合は、**プロセス開始時に無操作時間を告知**する

```text
推奨順：
1. 20時間超データを保持する（告知不要）
2. セッションタイムアウトを20時間以上にする
3. タイムアウトがある場合、プロセス開始時に無操作時間を告知する
```

> **参照**
> - [Understanding SC 2.2.6 — Sufficient Techniques](https://www.w3.org/WAI/WCAG22/Understanding/timeouts.html#techniques)

## プロセス開始時に無操作時間を告知する

- 関連するタスクやプロセスの**最初**に、無操作で切れるまでの時間を表示する
- **各ステップごと**に繰り返し表示する必要はない
- セキュリティ目的のタイムアウトであることも伝えるとよい
- 具体的な時間（例：1時間、15分）を明示する

```html
<!-- 良い例：手続き開始時に無操作タイムアウトを告知 -->
<section aria-labelledby="timeout-notice-heading">
  <h2 id="timeout-notice-heading">セッションについて</h2>
  <p>
    セキュリティのため、<strong>1時間以上操作がない場合</strong>、
    セッションが切れ入力内容が失われることがあります。
    休憩が必要な場合は、事前にメモを取るか下書き保存機能をご利用ください。
  </p>
</section>

<form action="/tax-return/step-1" method="post">
  <!-- 確定申告などの長い手続き -->
</form>
```

```html
<!-- 悪い例：タイムアウト直前にしか知らせない -->
<!-- 2.2.6 はプロセス開始時の告知を求める -->
<dialog id="timeout-warning" open>
  <p>あと1分でセッションが切れます。</p>
</dialog>
<!-- 開始時に「何分無操作で切れるか」を伝えていない -->
```

> **参照**
> - [Understanding SC 2.2.6 — tax return example](https://www.w3.org/WAI/WCAG22/Understanding/timeouts.html#examples)

## 20時間超のデータ保持

- ユーザーが何も操作しなくても、入力データを20時間超保持する
- この場合、無操作時間の告知は不要
- ECサイトの購入手続きで、カートや入力内容を24時間保持する例

```javascript
// 良い例：下書きを24時間保持
async function saveDraft(formData) {
  await fetch("/api/drafts", {
    method: "POST",
    headers: { "Content-Type": "application/json" },
    body: JSON.stringify({
      data: formData,
      expiresAt: Date.now() + 24 * 60 * 60 * 1000, // 24時間
    }),
  });
}
```

```text
良い例：
  購入手続きの入力内容を24時間サーバーに保存
  申請フォームの下書きを翌日まで保持

悪い例：
  30分で下書きを自動削除し、開始時にも告知しない
```

> **参照**
> - [Understanding SC 2.2.6 — e-commerce example](https://www.w3.org/WAI/WCAG22/Understanding/timeouts.html#examples)

## タイムアウトを設けない設計

- オンライン問い合わせフォームなど、タイムアウト処理がない場合
- ブラウザを閉じない限り、いつでも送信できる
- この場合も2.2.6に適合しうる

```html
<!-- 良い例：タイムアウトなしの問い合わせフォーム -->
<form action="/contact" method="post">
  <label for="message">お問い合わせ内容</label>
  <textarea id="message" name="message"></textarea>
  <button type="submit">送信</button>
</form>
<!-- セッションタイムアウトを実装していない -->
```

> **参照**
> - [Understanding SC 2.2.6 — contact form example](https://www.w3.org/WAI/WCAG22/Understanding/timeouts.html#examples)

## プライバシーとデータ保持

- データ保持による適合を検討する場合、プライバシー規制への配慮が必要
- 認証前・データ保存前に**明示的な同意**が求められる場合がある
- 未成年者の場合、多くの法域で同意取得が制限される
- PCI DSS（決済カード業界のセキュリティ基準）や HIPAA（米国の医療情報保護法）なども関連
- 法務・プライバシー専門家への相談を推奨

```text
注意点：
  個人情報の保存期間と削除方針を明確にする
  認証前のデータ保持は同意取得が必要な場合がある
  センシティブデータは暗号化・短期保持を検討する
```

> **参照**
> - [Understanding SC 2.2.6 — Note on privacy regulations](https://www.w3.org/WAI/WCAG22/Understanding/timeouts.html)

## 適用範囲と対象外

- **コンテンツ提供者が把握・制御できるタイムアウト**にのみ適用
- ユーザーがブラウザや端末を閉じて未送信データを失う場合は対象外
- インターネット接続の切断など、作者の制御外の事象は対象外

```text
適用される例：
  サイトが設定するセッションタイムアウト（15分無操作）
  アプリが実装するフォーム入力の有効期限

適用されない例：
  ユーザーがブラウザを閉じて未送信のフォームを失う
  ネットワーク切断による通信エラー
```

> **参照**
> - [Understanding SC 2.2.6 — Intent](https://www.w3.org/WAI/WCAG22/Understanding/timeouts.html#intent)

## 2.2.1・2.2.3・2.2.5 との関係

| 達成基準 | 焦点 | 関係 |
|---|---|---|
| 2.2.1 タイミング調整可能 | 時間制限のオフ・調整・延長 | 切れる前に延長できるか（A） |
| 2.2.3 タイミング非依存 | タイミングを不可欠にしない | 時間制限自体を避ける（AAA） |
| 2.2.5 再認証 | 再認証後のデータ保持 | 切れたあとに復元できるか（AAA） |
| 2.2.6 タイムアウト | 無操作タイムアウトの事前告知 | 切れる可能性を最初に知らせる（AAA） |

- 2.2.6 は 2.2.1 と連携するが、**無操作によるタイムアウトの告知**に特化
- 2.2.1 は「延長できるか」、2.2.6 は「最初から何分無操作で切れるか知っているか」
- 2.2.5 は「切れたあと復元」、2.2.6 は「切れる前に知らせる」
- 理想は、切れにくく（2.2.1 / 2.2.3）、切れても復元（2.2.5）、かつ事前告知（2.2.6）

```text
2.2.1 では適合しうるが 2.2.6 では不適合になりうる例：
  セッション延長はできるが、開始時に無操作時間を告知していない
  タイムアウト直前の警告のみで、プロセス開始時の告知がない

2.2.6 に適合しやすい例：
  購入手続き開始時に「1時間無操作でセッション切れ」と表示
  下書きを24時間保持し、告知不要
  タイムアウトを実装しない問い合わせフォーム
```

> **参照**
> - [wcag/2-2-1-timing-adjustable.md — 2.2.1 タイミング調整可能](./2-2-1-timing-adjustable.md)
> - [wcag/2-2-5-re-authenticating.md — 2.2.5 再認証](./2-2-5-re-authenticating.md)

## よくある失敗例

- セッションタイムアウトがあるのに、無操作時間を最初に伝えない
- タイムアウト直前の警告だけで、プロセス開始時の告知がない
- 「しばらく操作がないと切れます」など、具体的な時間が不明
- 各ステップごとに同じ警告を繰り返し、かつ開始時の告知がない
- 20時間未満でデータを削除し、告知もない

```html
<!-- 悪い例：曖昧な告知 -->
<p>しばらく操作がないとセッションが切れる場合があります。</p>

<!-- 良い例：具体的な時間を明示 -->
<p>15分間操作がないと、セッションが切れ入力内容が失われます。</p>
```

```javascript
// 悪い例：各ステップで警告するが、開始時の告知がない
function onStepChange(step) {
  showToast("操作がないとセッションが切れます"); // 毎ステップ
}

// 良い例：プロセス開始時に一度だけ告知
function onProcessStart() {
  showNotice("1時間無操作でセッションが切れます。この画面は最初に一度だけ表示されます。");
}
```

## 実装時の注意点

- 告知は関連プロセスの**最初**に一度表示する
- 時間は**具体的な数値**（分・時間）で示す
- 20時間超のデータ保持が可能なら、それが最も望ましい
- セキュリティ上の理由でタイムアウトが必要な場合も、告知は必須
- プライバシー規制に配慮し、データ保持方針を文書化する
- 告知と併せて、下書き保存や延長手段（2.2.1）も提供するとよい

```html
<!-- 良い例：告知 + 下書き保存の案内 -->
<aside aria-labelledby="session-info">
  <h2 id="session-info">ご利用上の注意</h2>
  <p>
    セキュリティのため、<strong>30分間操作がない場合</strong>にセッションが切れます。
    入力内容は自動で下書き保存されます。再ログイン後に続きから再開できます。
  </p>
</aside>
```

## テスト・確認方法

### 手動テスト

- ログインや入力が必要なプロセスを開始する
- プロセス開始時に、無操作で切れるまでの時間が告知されているか確認
- 告知が各ステップではなく、プロセスの最初に表示されているか確認
- 20時間超データ保持の場合は、告知なしでも適合しうることを確認
- タイムアウト後にデータが失われる場合、2.2.5（再認証後の復元）も確認

```text
チェックリスト：
1. 無操作でデータ損失につながるタイムアウトがあるか
2. 20時間超データを保持しているか（保持なら告知不要）
3. 保持しない場合、プロセス開始時に無操作時間を告知しているか
4. 告知の時間が具体的か（「しばらく」ではないか）
5. 告知がプロセス開始時に一度表示されているか
```

### 開発者ツールでの確認

```bash
# セッション・タイムアウト・告知まわりの実装を確認
rg "timeout|session|inactivity|無操作|セッション" --glob "*.js" --glob "*.tsx" --glob "*.jsx" --glob "*.php" --glob "*.html"
```

> **参照**
> - [a11y/manual-testing-checklist.md — 手動テストチェックリスト](../a11y/manual-testing-checklist.md)

## まとめ

- 2.2.6 は、無操作によるタイムアウトでデータが失われる可能性がある場合、**その無操作時間を事前に告知**することを求める達成基準（レベル AAA）
- 20時間超データを保持する場合は告知不要
- 告知は関連プロセスの**開始時に一度**、**具体的な時間**で行う
- 2.2.1（延長）・2.2.3（時間非依存）・2.2.5（再認証後の復元）と併せて設計する
- プライバシー規制への配慮が必要な場合がある

# WCAG2ICTについて — Web以外の文書やソフトウェアへWCAGを当てはめる考え方

## WCAG2ICTとは

**WCAG2ICT** は、Web Content Accessibility Guidelines（WCAG）を、Web以外の情報通信技術へ適用するときの考え方を示すW3Cのガイド。

- 正式名称は **Guidance on Applying WCAG 2 to Non-Web Information and Communications Technologies**
- 非Web文書と非Webソフトウェアを主な対象にする
- WCAG 2.0、2.1、2.2のレベルA・AAを扱う
- WCAGの原文を引用し、Web固有の言葉をどう読み替えるか、追加で何に注意するかを達成基準ごとに説明する
- W3C Recommendationではなく、要件を定めない **W3C Group Note**

2026年10月24日時点の完成版は、2025年12月11日公開のGroup Note。最新版を指すURLとして `https://www.w3.org/TR/wcag2ict/` を使える。

> 参照:
> - [W3C — WCAG2ICT](https://www.w3.org/TR/wcag2ict/)
> - [W3C — WCAG2ICT Overview](https://www.w3.org/WAI/standards-guidelines/wcag/non-web-ict/)

## なぜWCAGをそのまま読めないのか

WCAGは技術に依存しない書き方を重視しているが、Webを前提にした用語と適合モデルを持つ。

- `Web page` や `set of Web pages` という評価単位がある
- ブラウザなどの `user agent` がコンテンツを提示することを想定する
- Web技術がアクセシビリティサポートされているかを考える
- ページ全体、一連のプロセス、適合レベルなどを組み合わせて適合を判断する

PDF、プレゼンテーション、電子書籍、デスクトップアプリ、ネイティブモバイルアプリには、Webページやブラウザと同じ境界がない。ソフトウェア自身が画面を描画し、OSのアクセシビリティAPIを介して支援技術へ情報を渡す場合もある。

WCAG2ICTはWCAGを別の規格へ作り替えるのではなく、**WCAGの意図を保ったまま、非Web環境で用語と前提をどう解釈するか** を整理する。

> 参照: [W3C — WCAG2ICT, Guidance in This Document](https://www.w3.org/TR/wcag2ict/#guidance-in-this-document)

## WCAG2ICTは規格ではない

WCAG2ICTの位置づけを、WCAGや各地域のICT規格と分ける。

| 資料 | 役割 | 適合の扱い |
|---|---|---|
| WCAG 2 | Webコンテンツの達成基準と適合要件を定めるW3C Recommendation | WCAGの適合要件に基づいて判断する |
| WCAG2ICT | WCAGを非Web文書・ソフトウェアへ適用する場合の参考ガイド | **WCAG2ICT自体には適合できない** |
| EN 301 549 | 欧州のICTアクセシビリティ規格 | 規格が対象、適用要件、例外、評価を定める |
| Revised Section 508 Standards | 米国連邦機関のICTアクセシビリティ基準 | 法令・調達基準が適用範囲と要件を定める |

次のような表現は避ける。

```md
<!-- 不正確 -->
このアプリはWCAG2ICTに準拠しています。

<!-- 対象と根拠を明示する -->
このアプリをEN 301 549 V4.1.1の適用要件に基づいて評価しました。
WCAG由来の非Webソフトウェア要件の解釈では、WCAG2ICTを参照しました。
```

WCAG2ICTは、法令や製品要件の代わりではなく、**別の規格や方針がWCAGを非Webへ採用するときの解釈資料** として使う。

> 参照:
> - [W3C — WCAG2ICT, Comments on Conformance](https://www.w3.org/TR/wcag2ict/#comments-on-conformance)
> - [W3C — WCAG2ICT, Background](https://www.w3.org/TR/wcag2ict/#background)

## 対象になるもの

WCAG2ICTは、非Web ICTのうち **文書** と **ユーザーインターフェースを持つソフトウェア** を中心に扱う。

### 非Web文書

- PDF
- ワープロ文書
- スプレッドシート
- プレゼンテーション
- メール
- 電子書籍
- 画像、動画など、利用者から一つの文書として扱われるコンテンツ

WCAG2ICTでいう文書は、コンテンツを提示するために別のユーザーエージェントを必要とする。PDFならPDFビューア、プレゼンテーションなら対応する閲覧ソフトが必要になる。

### 非Webソフトウェア

- WindowsやmacOSのデスクトップアプリ
- iOSやAndroidのネイティブアプリ
- プラットフォームソフトウェア
- キオスク端末やATMなどで動くソフトウェア部分
- プリンター、スマートテレビ、医療機器などの画面を持つソフトウェア部分
- コマンドライン、ターミナルで操作するアプリケーション

ソフトウェアは、自身のUIと埋め込まれたコンテンツを提示する。ユーザーインターフェースを持たないドライバーやファームウェアだけを、WCAG2ICTのソフトウェアとして評価するわけではない。

> 参照: [W3C — WCAG2ICT, Key Terms](https://www.w3.org/TR/wcag2ict/#key-terms)

## 対象外・不足する範囲

WCAG2ICTだけで、ICT製品全体のアクセシビリティを保証することはできない。

| 範囲 | WCAG2ICTでの扱い |
|---|---|
| ハードウェア | 対象外。操作部、接続端子、到達範囲などは別の基準が必要 |
| 実装技法 | PDF、Office、iOSなどの具体的な作り方は提供しない |
| 達成基準の採否 | どの達成基準を製品へ要求するかは決めない |
| 法的義務 | 法令の対象、例外、罰則、適合方法は決めない |
| WCAG外の利用者ニーズ | WCAGが扱わない要求を補うものではない |
| Webコンテンツ | 通常のWCAGと、そのWeb向け解説・技法を使う |

たとえば券売機では、画面ソフトウェアのコントラストやフォーカスだけでなく、物理キー、カード挿入口、イヤホン端子、設置高さ、内蔵音声なども必要になる。これらをWCAG2ICTだけで評価しない。

> 参照: [W3C — WCAG2ICT, Excluded from Scope](https://www.w3.org/TR/wcag2ict/#excluded-from-scope)

## 重要な用語の読み替え

WCAG2ICTを読むときは、最初にKey Termsを確認する。日常的な意味と評価上の意味が異なる場合がある。

| WCAGの前提 | WCAG2ICTでの読み替え |
|---|---|
| Web page | 非Web文書、またはソフトウェアプログラム |
| Set of Web pages | 文書の集合、またはソフトウェアプログラムの集合 |
| User agent | 文書を提示する閲覧ソフト。ソフトウェアではソフトウェア自身が同等の機能を担う場合がある |
| Content | 文書またはソフトウェアで利用者へ伝える情報・感覚的体験。ソフトウェアではUIも含む |
| WebのアクセシビリティAPI | Platform softwareのaccessibility services |

### 一つの文書

文書は、一つのファイルとは限らない。動画、音声、字幕、タイミング情報が複数ファイルに分かれていても、利用者に一つの作品として提示されるなら、一つの文書になり得る。

一方、ZIPへ複数の独立した文書をまとめただけでは、一つの文書にならない。ファイル形式ではなく、**利用者に一つの項目として機能するか** を見る。

### 文書の集合

単に同じフォルダーへ置いた文書すべてではない。共通の目的があり、同じ作成者・組織が一緒に公開し、各文書から互いを名前やリンクで参照するような集合を指す。

### ソフトウェアプログラム

非WebソフトウェアをWebページのように画面単位で明確に切り分けることは難しい。そのため、WCAG2ICTでは一つのWebページに相当する評価単位を **ソフトウェアプログラム全体** として考える。

複数のソフトウェアプログラムがWCAG2ICTの定義する「集合」になるケースは、非常にまれとされる。

> 参照:
> - [W3C — WCAG2ICT, Document](https://www.w3.org/TR/wcag2ict/#document)
> - [W3C — WCAG2ICT, Set of Documents](https://www.w3.org/TR/wcag2ict/#set-of-documents)
> - [W3C — WCAG2ICT, Software](https://www.w3.org/TR/wcag2ict/#software)

## 達成基準ごとの読み方

WCAG2ICTはWCAGと同じく、知覚可能、操作可能、理解可能、堅牢の順に構成される。各達成基準では、次の順に読む。

1. 引用されたWCAGの達成基準を読む
2. `Applying SC ... to Non-Web Documents and Software` を読む
3. 文書とソフトウェアで節が分かれていないか確認する
4. Web固有語の置換を確認する
5. `Note (Added)` とclosed functionalityへの参照を確認する
6. 対象の規格が、その達成基準を採用・除外・変更していないか確認する

適用のされ方は、大きく分けて次の形になる。

| 形 | 例 |
|---|---|
| そのまま適用 | 1.1.1 非テキストコンテンツ、1.3.1 情報及び関係性、3.3.1 エラーの特定 |
| Web用語を置換 | 2.4.3 フォーカス順序で `web page` を文書またはソフトウェアへ置換 |
| 文書とソフトウェアで説明を分ける | 2.1.1 キーボード、2.4.2 ページタイトル |
| 非Web固有の注記を追加 | 1.4.10 リフロー、4.1.2 名前・役割・値 |
| WCAGの版により扱いが変わる | 4.1.1 構文解析はWCAG 2.2で廃止 |

> 参照: [W3C — WCAG2ICT, Comments by Guideline and Success Criterion](https://www.w3.org/TR/wcag2ict/#comments-by-guideline-and-success-criterion)

## 文書へ当てはめる例

PDF、ワープロ、プレゼンテーションなどでは、見た目だけでなく、閲覧ソフトと支援技術が利用できる構造・順序・メタデータを見る。

| 達成基準 | 非Web文書で確認する例 |
|---|---|
| 1.1.1 非テキストコンテンツ | 意味のある画像に代替テキストがある |
| 1.3.1 情報及び関係性 | 見出し、リスト、表、フォームラベルが構造として伝わる |
| 1.3.2 意味のある順序 | 読み上げ順が内容の意味を保つ |
| 1.4.3 コントラスト | 文字と背景に必要なコントラストがある |
| 1.4.10 リフロー | 拡大や表示領域の変更で、情報・機能を失わず読める |
| 2.4.2 ページタイトル | 対応形式では、編集可能なTitleプロパティに内容を表す題名がある |
| 3.1.1 ページの言語 | 文書の既定言語をプログラムが判別できる |
| 4.1.2 名前・役割・値 | フォーム部品の名前、役割、状態を支援技術が取得できる |

### ファイル名と文書タイトルを分ける

```text
ファイル名: report-final-v3.pdf
文書のTitleプロパティ: 2026年度 アクセシビリティ評価報告書
```

ファイル名は保存・管理の都合で変わり、内容の目的を十分に表さないことがある。形式と一般的な作成ツールがプログラムで取得できるTitleプロパティを扱える場合は、そのプロパティへ適切な題名を設定する。

### 作成ツールだけでなく閲覧環境も見る

文書は、閲覧ソフトを通して提示される。

- 文書形式が構造、言語、代替テキストを保持できるか
- 作成ツールから正しく書き出せるか
- 対象のPDFビューアやOfficeアプリが情報をアクセシビリティAPIへ公開するか
- スクリーンリーダー、拡大、キーボード操作と組み合わせて利用できるか
- 変換や結合の工程でタグ、読み順、フォーム情報が失われないか

文書ファイル単体の検査結果だけでなく、利用者が実際に使う閲覧環境を含めて評価する。

> 参照:
> - [W3C — Applying SC 1.3.1 to Non-Web Documents and Software](https://www.w3.org/TR/wcag2ict/#applying-sc-131-info-and-relationships-to-non-web-documents-and-software)
> - [W3C — Applying SC 2.4.2 to Non-Web Documents](https://www.w3.org/TR/wcag2ict/#applying-sc-242-page-titled-to-non-web-documents)

## ソフトウェアへ当てはめる例

ネイティブアプリでは、HTMLやARIAの有無ではなく、利用するUIフレームワークとOSのアクセシビリティサービスを通じて、同じ利用者ニーズを満たす。

| 達成基準 | 非Webソフトウェアで確認する例 |
|---|---|
| 1.3.1 情報及び関係性 | 見出し、グループ、表、ラベルの関係をAPIへ公開する |
| 1.4.10 リフロー | ウィンドウ幅、表示倍率、解像度の変更で情報や操作を失わない |
| 2.1.1 キーボード | プラットフォームが機器非依存のキーボードインターフェースを提供する場合、機能をキーボードで使える |
| 2.4.3 フォーカス順序 | 順次移動の順序が意味と操作を保つ |
| 2.4.7 フォーカスの可視化 | キーボードフォーカスを視覚的に確認できる |
| 2.5.8 ターゲットのサイズ | ポインターで操作する対象の大きさ・間隔を確認する |
| 3.3.1 エラーの特定 | エラーの箇所を特定し、テキストで説明する |
| 4.1.2 名前・役割・値 | コントロールの名前、役割、状態、値、変更通知をAPIへ公開する |

### プラットフォームのアクセシビリティサービスを使う

WebではDOMとアクセシビリティツリーが中心になるが、ネイティブアプリではUI Automation、NSAccessibility、Android Accessibility、iOS Accessibilityなど、プラットフォームの仕組みを使う。

- 標準UIコンポーネントを優先する
- 独自描画したコントロールは、名前、役割、値、状態、操作を明示する
- 値や状態が変わったとき、支援技術へイベントを通知する
- 画面遷移、ダイアログ、項目削除後のフォーカスを管理する
- OSの文字サイズ、ズーム、コントラスト、動きを減らす設定を尊重する

Web向けのARIA属性をネイティブUIへ移植するのではなく、そのプラットフォームで同じセマンティクスと操作を公開する。

### ソフトウェア全体を評価する

画面単位だけで合格率を集計すると、設定、更新、ログイン、ファイル選択など、主要タスクに必要な別画面を落としやすい。

- プログラムに含まれる画面とモードを洗い出す
- 利用者が目的を完了する一連のプロセスを特定する
- 共通コンポーネントを試験しつつ、実際の画面への組み込みも確認する
- 権限確認、OS標準ダイアログ、埋め込みWebビュー、外部認証も境界を記録する
- 対象外にした機能と理由を残す

> 参照:
> - [W3C — WCAG2ICT, Accessibility Services of Platform Software](https://www.w3.org/TR/wcag2ict/#accessibility-services-of-platform-software)
> - [W3C — WCAG2ICT, Comments on Conformance](https://www.w3.org/TR/wcag2ict/#comments-on-conformance)

## closed functionalityの扱い

**Closed functionality** は、利用者が支援技術を接続、インストール、利用できない特性を指す。

- ATMや券売機
- セルフレジやPOS端末
- プリンターの操作パネル
- スマートテレビやゲーム機
- 一部の医療機器、IoT機器
- OSへのログイン前など、支援技術をまだ起動できない部分

この環境では「情報をアクセシビリティAPIへ公開し、利用者のスクリーンリーダーに読ませる」という方法を使えない場合がある。内蔵音声、触覚で識別できる操作部、画面拡大など、製品自身がアクセシビリティ機能を提供する必要がある。

WCAG2ICTにはclosed functionalityで問題になりやすい達成基準の解説があるが、ハードウェア要件や内蔵機能に必要なすべての要件を定めてはいない。EN 301 549やSection 508など、製品全体を扱う基準と組み合わせる。

> 参照:
> - [W3C — WCAG2ICT, Closed Functionality](https://www.w3.org/TR/wcag2ict/#closed-functionality)
> - [W3C — Success Criteria Problematic for Closed Functionality](https://www.w3.org/TR/wcag2ict/#success-criteria-problematic-for-closed-functionality)

## 達成基準の「適用なし」をWCAG2ICTだけで決めない

WCAG2ICTは「この種類の製品では、どの達成基準を要求しないか」を決める文書ではない。適用するならどう解釈するかを示す。

また、WCAGの適合モデルでは、対象となる内容が存在しなければ、その達成基準を失敗していないため満たした扱いになる。たとえば音声がない文書は、字幕を用意できないという理由で不適合になるわけではない。

一方、EN 301 549やACRなどの評価表では、前提条件により `Not applicable` と記録する運用がある。次の状態を混同しない。

| 状態 | 意味 |
|---|---|
| 満たしている | 適用される条件があり、要求を満たす |
| 対象となる内容がない | WCAGの考え方では、その達成基準を失敗していない |
| 規格上の適用なし | 採用した規格の前提条件・対象範囲により適用されない |
| 未評価 | 確認していない。適用なしにはできない |

最終的な記録方法は、適用する規格、法令、契約、評価様式に従う。

> 参照: [W3C — WCAG2ICT, Comments on Conformance](https://www.w3.org/TR/wcag2ict/#comments-on-conformance)

## 2013年版と現在版を分ける

| 版 | 対象 |
|---|---|
| 2013年版 WCAG2ICT | WCAG 2.0のレベルA・AA |
| 現在版 WCAG2ICT | WCAG 2.0、2.1、2.2のレベルA・AA |

古い法令や規格が2013年版の考え方を基にしていても、WCAG2ICTの最新版へ自動的に切り替わるわけではない。

- 契約・法令が引用するWCAGと規格の版を確認する
- 最新のWCAG2ICTは新しい達成基準の設計・評価資料として使う
- 法的最低要件と、製品として採用する現在の目標を分ける
- WCAG 2.2では4.1.1「構文解析」が廃止されているが、WCAG 2.0・2.1を引用する基準では扱いを確認する

> 参照:
> - [W3C — WCAG2ICT publication history](https://www.w3.org/standards/history/wcag2ict-22/)
> - [W3C — WCAG2ICT 2.0 Group Note](https://www.w3.org/TR/wcag2ict-20/)

## 実務での使い方

### 1. 適用根拠と版を決める

```md
## 評価基準

- 製品: デスクトップアプリ 4.2
- 対象OS: Windows 11 / macOS 26
- 要求規格: EN 301 549 V4.1.1
- WCAG由来の要件: WCAG 2.2 レベルA・AA
- 解釈資料: WCAG2ICT 2025-12-11 Group Note
- 対象: インストール、ログイン、編集、書き出し、設定、ヘルプ
- 対象外: サーバーの管理用CLI（理由と責任範囲を別記）
```

「WCAG2ICTを基準にした」だけでは、適用する達成基準、適合レベル、例外、法的根拠が決まらない。

### 2. ICTを分類する

- Webコンテンツ
- 非Web文書
- 非Webソフトウェア
- ハードウェア
- closed functionality
- サポート文書・サポートサービス

一つの製品が複数にまたがる場合は、部分ごとに適用する資料を分ける。ElectronアプリやWebViewを使うアプリでも、「すべてWeb」または「すべて非Web」と短絡せず、配布形態、実行環境、評価規格の定義を確認する。

### 3. 達成基準を読み替える

- WCAGの達成基準とIntentを確認する
- WCAG2ICTの `Applying...` と追加注記を読む
- 文書、ソフトウェア、closed functionalityで説明が違う箇所を分ける
- 使用技術の具体的な実装方法を、プラットフォーム公式資料などで調べる
- 適用する規格が除外や追加要件を持つか確認する

### 4. 実環境で評価する

| 対象 | 評価環境に含めるもの |
|---|---|
| 文書 | 作成・変換後のファイル、閲覧ソフト、OS、支援技術 |
| ソフトウェア | 製品版、OS、UIフレームワーク、入力方法、支援技術 |
| closed functionality | 実機、内蔵アクセシビリティ機能、物理操作部、設置条件 |

自動検査だけでなく、キーボード、スクリーンリーダー、拡大、配色、音声・字幕、タッチ、主要タスクの手動試験を組み合わせる。

### 5. 解釈と証拠を残す

```md
| 要件 | 対象 | 判定 | 根拠 |
|---|---|---|---|
| 1.3.1 | 設定画面 | Pass | ラベルと入力欄の関係をUI Automationで確認 |
| 1.4.10 | 編集画面 | Fail | 200%表示時に保存ボタンが画面外へ隠れる |
| 1.2.2 | アプリ全体 | 対象となる内容なし | 同期済み音声を含む動画が存在しない |
```

- WCAG2ICTの参照箇所
- 適用規格の条項
- 対象製品の版
- OS、閲覧ソフト、支援技術の版
- 手順、期待結果、実際の結果
- 適用なしや対象外にした理由

を結び付ける。将来の更新で再評価する範囲を判断しやすくなる。

## EN 301 549・Section 508との関係

WCAG2ICTは、WCAGを非Webへ取り込む規格づくりに影響を与えてきた。

| 観点 | WCAG2ICT | EN 301 549 / Section 508 |
|---|---|---|
| 文書の種類 | 参考ガイド | 規格・法的基準 |
| 主な役割 | WCAGの意図と用語を非Webへ読み替える | 適用対象、要求事項、例外、評価を定める |
| ハードウェア | 対象外 | 条件に応じて対象 |
| WCAG外の要件 | 網羅しない | ソフトウェア、文書、ハードウェア、サポートなどを追加 |
| 適合 | WCAG2ICT自体への適合はない | 各制度のルールで判断する |

したがって、調達や監査では次の順序になる。

1. 適用される法令・規格・契約を確認する
2. その文書が引用するWCAGの版と対象要件を確認する
3. 非Web向けの条項と例外を確認する
4. 解釈が必要な箇所でWCAG2ICTを参照する
5. 規格が要求する方法で結果を報告する

## まとめ

- WCAG2ICTは、WCAG 2.0、2.1、2.2のレベルA・AAを非Web文書とソフトウェアへ適用する考え方を示すW3C Group Note
- 規格や法令ではなく、WCAG2ICT自体への適合や準拠を宣言するものではない
- `Web page` を文書またはソフトウェアへ読み替え、ユーザーエージェントやアクセシビリティAPIの前提も非Web環境に合わせて解釈する
- PDF、Office文書、ネイティブアプリなどが対象になり得るが、ハードウェアと具体的な実装技法は対象外
- ソフトウェアは画面単位ではなく、プログラム全体を評価単位として考える
- closed functionalityでは内蔵アクセシビリティやハードウェア要件が必要になり、WCAG2ICTだけでは不足する
- 実務では、先に適用規格と版を決め、WCAG2ICTを解釈資料として使い、対象環境・結果・根拠を記録する

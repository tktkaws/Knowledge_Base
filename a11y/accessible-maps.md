# 地図情報のアクセシブルな出し方 — 埋め込み地図だけに頼らない

## 地図情報と WCAG の関わり

- アクセスページの地図は「場所がどこか」を伝えるための情報であり、装飾ではない
- 地図まわりで特に意識したい達成基準の例

| 達成基準 | レベル | 地図での意味 |
|---|---|---|
| 1.1.1 非テキストコンテンツ | A | 地図が伝える情報を、テキストでも同等に提供する |
| 2.1.1 キーボード操作可能 | A | 操作が必要な UI はキーボードだけで使えること |
| 2.4.1 ブロックスキップ | A | `iframe` には内容が分かる `title` を付ける（H64） |
| 1.4.11 非テキストのコントラスト | AA | 地図上のラベルや操作 UI のコントラスト |

- 「地図を置いたから対応完了」ではない — **地図の目的（所在地・道順）をテキストでも届ける**のが要点
- 本記事では、Google マップ埋め込みの限界と、実務で参考になる出し方を整理する

> 参照: [WCAG 2.2 — Non-text Content](https://www.w3.org/WAI/WCAG22/Understanding/non-text-content) / [H64: Using the title attribute of the iframe element](https://waic.github.io/wcag22/Techniques/H64.html)

## Google マップ埋め込みはアクセシブルなのか

- 結論から言うと、**埋め込み単体では十分ではない**
- スクリーンリーダー利用者にとって、地図キャンバス自体は場所情報として読み取りにくい
- キーボード操作でも問題が出やすい
  - フォーカス順が直感的でない
  - 一部コントロールがキーボードから届かない・名前がない、といった報告がある
- `iframe` に `title` を付けるのは最低限の対応 — それだけでは「住所・道順が伝わる」ことにはならない

```html
<!-- 悪い例：title がなく、何の iframe か分からない -->
<iframe src="https://www.google.com/maps/embed?..." width="600" height="450"></iframe>

<!-- 良い例：title で目的を示す。ただしこれだけでは不十分 -->
<iframe
  src="https://www.google.com/maps/embed?..."
  title="本社オフィスの所在地を示す地図"
  width="600"
  height="450"
></iframe>
```

- 埋め込みは「視覚的な補助」として使う前提が現実的
- 住所・最寄駅・徒歩分・道順は、ページ本文のテキストで必ず提供する
- Google マップ本体へのリンクも併記すると、アプリ連携や詳細ルート確認に役立つ

> 参照: [Vision Australia — Embedded YouTube and Google Maps](https://www.visionaustralia.org/business-consulting/digital-access/blog/embedded-youtube-and-google-maps) / [Carnegie Museums — Maps](http://web-accessibility.carnegiemuseums.org/content/maps/)

## 実務例1: ミツエーリンクス

- アクセシビリティに強い制作会社として知られるミツエーリンクスの本社アクセスは、**テキスト中心**になっている
- 構成の要点
  - 「Google マップで見る」リンクを用意する
  - 所在地（郵便番号・住所・建物名・階）を本文で示す
  - 最寄駅と徒歩時間をリストで示す
  - 駅からの道順を、出口名・目印・エレベーター名まで文章で書く
- 地図画像や埋め込みに情報を閉じ込めず、**読むだけで到着手順が分かる**設計
- 視覚的な地図は補助、テキストが本体、という優先順位がはっきりしている

> 参照: [ミツエーリンクス — 本社 交通アクセス](https://www.mitsue.co.jp/company/access/head_office.html)

## 実務例2: デジタル庁

- デジタル庁の組織情報ページも、アクセス情報を**テキストで完結**させている
- 所在地・電話番号などを箇条書きで提示し、埋め込み地図に依存していない
- 地図 UI のキーボード操作やコントラスト問題を、ページ側で抱え込まない選択とも読める
- 「地図を載せるかどうか」より先に、「住所情報がテキストとして一意に取れるか」を満たしている

> 参照: [デジタル庁 — 組織情報](https://www.digital.go.jp/about)

## アクセシブルな地図情報の出し方

- 推奨パターン（埋め込みの有無にかかわらず）

1. 所在地をテキストで書く — 郵便番号、住所、建物名、階数
2. 交通手段をテキストで書く — 路線、駅、出口、徒歩時間
3. 必要なら道順を文章で補う — 目印や曲がり角を含める
4. Google マップなど外部地図へのリンクを置く — リンク文言は「Google マップで見る」など具体的に
5. 埋め込む場合は `iframe` に具体的な `title` を付ける
6. 地図の直前に見出しを置き、何の地図かを文脈でも示す

```html
<section aria-labelledby="access-heading">
  <h2 id="access-heading">アクセス</h2>

  <p>〒160-0000 東京都〇〇区〇〇1-2-3 〇〇ビル3階</p>
  <ul>
    <li>○○線「△△駅」出口1より徒歩5分</li>
  </ul>
  <p><a href="https://maps.google.com/?q=...">Google マップで見る（本社所在地）</a></p>

  <iframe
    src="https://www.google.com/maps/embed?..."
    title="本社所在地の地図"
    width="600"
    height="450"
    loading="lazy"
  ></iframe>
</section>
```

- 静的な地図画像だけを使う場合は、`alt` に住所や位置関係の要約を入れる
- 「地図があること」自体より、**同じ目的をテキストで果たせるか**が適合の判断軸になる

## まとめ

- 地図情報は WCAG の非テキストコンテンツ・キーボード・iframe の `title` など複数基準に関わる
- Google マップ埋め込みは便利だが、単体ではアクセシブルと言い切れない
- `title` 付与は最低限 — 住所・交通・道順のテキスト提供が本体
- ミツエーリンクスは、地図リンク＋詳細な道順テキストで情報を届けている
- デジタル庁は、所在地をテキストで完結させ、埋め込みに依存していない
- 実務では「テキストで届く情報を先に作り、地図は補助」の順で設計する

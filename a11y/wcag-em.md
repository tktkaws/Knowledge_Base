# WCAG-EMについて — 適合評価を5ステップで進める

## WCAG-EMとは

- WCAG-EM（WCAG Evaluation Methodology）は、デジタル製品が WCAG 2 にどの程度適合しているかを評価する手順
- 達成基準は増やさない — WCAG の追加要件にはならない
- 公開形態は W3C Group Note — 策定したワーキンググループは承認しているが、W3C や会員による勧告ではない
- 現行は WCAG-EM 2.0（2026年7月23日）
- 1.0 の対象はウェブサイトとウェブページ — 2.0 はウェブアプリ、ネイティブアプリ、キオスク、文書（PDF、EPUB など）まで含む
- 自己評価にも、第三者の監査にも使える
- 特定の検査ツール、ブラウザ、支援技術には依存しない
- 全画面を見る前の足がかりには Easy Checks を使う — WCAG-EM は本格的な適合評価の手順
- 使うには、WCAG、アクセシブルな実装、支援技術、障害のある人の利用のしかたについての知識が要る
- 障害のある利用者の参加は必須ではないが、強く推奨される — 専門家の評価だけでは拾いにくい障壁がある
- 開発の最後にだけ行う検査ではない — 計画、設計、実装の途中からアクセシビリティを入れる前提で、完成品の確認にこの手順を使う

> 参照: [WCAG-EM Overview](https://www.w3.org/WAI/test-evaluate/conformance/wcag-em/) / [WCAG-EM 2.0](https://www.w3.org/TR/wcag-em-2/) / [WCAG-EM 2.0 公開のお知らせ](https://www.w3.org/WAI/news/2026-07-23/wcag-em-2/) / [Easy Checks](https://www.w3.org/WAI/eval/preliminary)

## 評価の5ステップ

- 手順は5つ — 評価中に範囲やサンプルの不足が見つかるので、前のステップに戻ってよい
- 製品の種類と評価の目的によって、順番が前後することもある

| ステップ | やること |
|---|---|
| 1. 範囲を決める | 対象製品、適合レベル、アクセシビリティ サポーテッドのベースライン |
| 2. 製品を調べる | 共通画面、必須機能、画面の種類、依存している技術 |
| 3. サンプルを選ぶ | 構造化サンプル、無作為サンプル、プロセス全体 |
| 4. サンプルを評価する | 選んだ画面を、WCAG の5つの適合要件に照らして確認する |
| 5. 結果を報告する | 各ステップの結果を記録し、必要なら評価声明を出す |

### ステップ1: 範囲を決める

- どの画面が対象か、境界が曖昧にならないように書く — URI の一覧や正規表現が使えるとよい
- 第三者コンテンツ、言語版、モバイル版、別ドメインのショップを含めるかどうかも書く
- 範囲は閉じた単位にする — 一部を恣意的に外すと、WCAG の「ページ全体」と「プロセス全体」と衝突しやすい
- 例: 銀行サイト全体を対象にするなら、個人向け、法人向け、ログイン後、共通の免責とサイトマップまで含める
- 例: 「法人向け」だけを対象にするなら、その配下の機能と、そこから辿れる共通画面まで含める
- 適合レベルは A / AA / AAA から選ぶ — 一般的な目標は AA
- 目標より上の達成基準も、余裕があれば記録する — 次の改善に使える
- ベースラインは、想定する OS、ブラウザ、支援技術の組み合わせ — 依頼者と合意する
- イントラネットのように利用者と端末が決まっている場合は、その環境に絞ってよい
- 追加で知りたいこと（不適合の全件、改修案、利用者テストなど）があれば、この時点で合意して記録する

### ステップ2: 製品を調べる

- 共通画面 — ホームやログイン、ヘッダー、フッター、ナビから辿れる画面
- 必須機能 — それが無いと製品の目的が変わるもの（購入、フォーム送信、アカウント登録など）
- 画面の種類 — レイアウト、フォーム、表、動画、モーダル、カルーセル、テンプレート、エラー表示の違い
- 依存している技術 — HTML、CSS、JavaScript、WAI-ARIA、PDF、EPUB に加え、CMS、デザインシステム、フレームワークも版まで書くと後が楽
- 障害のある人に関係が深い画面 — アクセシビリティ機能の説明、ヘルプ、設定、問い合わせ、認証、個人情報、決済
- 必須機能を全部列挙する作業ではない — 代表的なサンプルを後で選ぶための一覧
- アカウントが無い、データが空、といった状態のままだと、この段階で評価が偏る

> 参照: [WCAG-EM 2.0 — Step 1](https://www.w3.org/TR/wcag-em-2/#step1) / [WCAG-EM 2.0 — Step 2](https://www.w3.org/TR/wcag-em-2/#step2)

## サンプルの選び方

- 画面が少ない製品や、画面に分けられない文書は、サンプリングを省略して全体を評価してよい
- それ以外は、全体を代表するサンプルを作る
- 数に決まった公式はない — 画面数、古さ、対話の多さ、実装のばらつき、結果に求める信頼度で増える
- 開発プロセスと教育が揃っている、CMS や著者が限られる、過去の評価がある、といった場合は少なくて済む

### 構造化サンプル

- ステップ2で挙げたものが、少なくとも1つは入るように選ぶ
  - 共通画面
  - 必須機能
  - 画面の種類
  - 依存している技術
  - ヘルプや認証など、障害のある人に関係が深い画面
- 1画面が複数を兼ねてよい — 代表を丁寧に選べば、数を抑えつつ全体をカバーできる

### 無作為サンプル

- 構造化サンプルの 10% を、まだ選んでいない画面から無作為に足す
- 分母は製品全体の画面数ではない — 構造化サンプルの件数
- 例: 構造化が 80 画面なら無作為は 8 画面 — 合計 88 画面
- 選び方に予測できる偏りを付けない — クロール、サーバログ、画面一覧からの抽選など、方法自体を記録する
- すでに選んだ画面と同じものが当たったら、別の画面に差し替える
- 役割は、構造化サンプルが全体を代表しているかの点検

### プロセス全体

- 選んだ画面が手続きの途中なら、その手続きの開始から完了までをサンプルに含める
- 既定の経路（入力ミスなし、追加オプションなし）に加え、よく使う分岐も含める — 配送先の追加など、本線に戻るまで
- URL だけでは再現できないことが多い — 次の画面へ進む操作を記録する

> 参照: [WCAG-EM 2.0 — Step 3](https://www.w3.org/TR/wcag-em-2/#step3)

## 評価と報告

### サンプルを評価する

- 物差しは、目標レベルにおける WCAG 2 の5つの適合要件
  - 適合レベル
  - ページ全体
  - プロセス全体
  - アクセシビリティ サポーテッドな技術の使用のみ
  - 非干渉
- 手続きの途中でない画面は、操作を始める前の状態で達成基準を確認する
- ヘッダーやナビなど繰り返す部品は、見た目や振る舞いが同じなら毎回やり直さなくてよい
- 該当するコンテンツが無い達成基準は、満たしている扱い — レポートでは「該当なし」と書いてもよい
- 代替版がある場合は、別サンプルにせず、元の画面とセットで1単位として見る
- 手続きの途中は、変化した部分と、入力、エラー、通知、設定の違いを見る
- W3C の達成方法集は使ってよいが、必須ではない — 達成基準を満たすか満たさないかを判定できればよい
- 無作為サンプルに、構造化サンプルに無い種類のコンテンツや新しい不適合が出たら、サンプルが代表になっていない — ステップ3に戻って足す

### 結果を報告する

- 各ステップの結果を残す — 評価者、依頼者、日付、範囲、適合レベル、ベースライン、依存技術、選んだ画面、無作為の選び方、評価結果
- 満たしていない達成基準は、少なくとも1例を載せる — 再現手順、重大度、スクリーンショットがあると改修が速い
- 公開するかは依頼者が決める — 評価の記録すべてを公開する必要はない
- 任意で、評価した画面の保管と、使ったブラウザ、支援技術、手法の記録を残す — 後から争点になったときの材料になる
- その記録には認証情報が含まれることがある — 扱いには注意する
- 評価声明（evaluation statement）に最低限書くもの — 発行日、WCAG の版と URI、適合レベル、対象製品の定義、依存技術、ベースライン
- 一部だけの適合として声明を出す場合、理由は第三者コンテンツか、言語に対するアクセシビリティ サポーテッドの不足に限る — 適合していない領域も書く
- 声明と報告書自体も、アクセシブルな形式で公開する
- 集計スコアは任意 — 進捗の目安にはなるが、誤解を招きやすい
- WCAG 2 に採点方式はない — 出すなら、算出方法をレポートと一緒に渡す
- 機械可読の報告には EARL（Evaluation and Report Language）が推奨される
- 手順に沿ったレポートの下書きには、WCAG-EM Report Tool がある

> 参照: [WCAG-EM 2.0 — Step 4](https://www.w3.org/TR/wcag-em-2/#step4) / [WCAG-EM 2.0 — Step 5](https://www.w3.org/TR/wcag-em-2/#step5) / [WCAG 2.2 解説書 — 適合](https://www.w3.org/WAI/WCAG22/Understanding/conformance) / [WCAG-EM Report Tool](https://www.w3.org/WAI/eval/report-tool/)

## サンプル評価と適合表明は別

- WCAG 2 の適合表明（conformance claim）は、表明の範囲にある各ページが適合要件を満たしていることが前提
- 一部のサンプルを見ただけでは、見ていない画面に不適合が残ることがある
- そのため、サンプリングだけでは、製品全体の WCAG 適合表明にはならない
- 出せるのは、この手順で評価した結果についての評価声明
- 評価したサンプルがすべて目標レベルを満たし、必須の手順を実施し、製品の所有者が声明の妥当性を保つ、という条件が揃ったときに声明を出せる
- 開発中の評価は、少しの変更で古くなる — 完成品についての表明には使わない
- 再評価では、前回のサンプルのおよそ半分を残し、残りを入れ替える — 大きな変更が無い限り、件数と選び方は維持する
- 多数の製品を自動検査中心で比べる調査は、この手順が求める定性的な深さには届かない

> 参照: [WCAG-EM 2.0 — Relation to WCAG 2 Conformance Claims](https://www.w3.org/TR/wcag-em-2/#context)

## まとめ

- WCAG-EM は WCAG 2 への適合を評価する手順で、達成基準そのものは増やさない
- 現行の 2.0 は、ウェブサイトに加え、アプリ、キオスク、文書も対象にする
- 手順は、範囲、探索、サンプル、評価、報告の5つ — 不足が見つかれば前に戻る
- サンプルは、構造化、無作為（構造化の 10% であり、全体の 10% ではない）、プロセス全体の3つを合わせる
- 評価は5つの適合要件に照らす — 無作為で新しい種類が出たら、サンプルを足し直す
- サンプル評価の結果は、製品全体の WCAG 適合表明にはならない
- 報告では各ステップを残す — 声明やスコアを出すなら、条件と算出方法を明示する

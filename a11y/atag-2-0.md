# ATAG 2.0について — オーサリングツール向けのアクセシビリティガイドライン

## ATAGとは

- **ATAG** = Authoring Tool Accessibility Guidelines（オーサリングツールのアクセシビリティガイドライン）
- 現行の規範は **ATAG 2.0**（W3C Recommendation、2015年9月24日）
- 対象は、Webコンテンツを作るソフトウェアとサービス
- 例: WYSIWYGエディタ、CMS、LMS、ノーコードのサイトビルダー、ブログ、Wiki、コメント欄、SNS、文書のHTML書き出し
- 読む相手は、ツールの開発者に加え、導入時にツールを選ぶ人、ベンダーへ改善を求める人
- 技術非依存。2015年公開で参照先は WCAG 2.0 だが、WAIは最新の WCAG 2 を使うよう案内している
- 更新の検討は ATAG Community Group で進んでいる

> 参照:
> - [W3C WAI — ATAG Overview](https://www.w3.org/WAI/standards-guidelines/atag/)
> - [W3C — ATAG 2.0](https://www.w3.org/TR/ATAG20/)

## WCAG・UAAGとの違い

| ガイドライン | 主な対象 | 問い |
|---|---|---|
| WCAG | 公開されるWebコンテンツ | 利用者がそのページを使えるか |
| ATAG | コンテンツを作るツール | 作成者はツールを使えるか。ツールはアクセシブルなコンテンツ作りを支えるか |
| UAAG | ブラウザなどのユーザーエージェント | 利用者の環境側はコンテンツを届けるか |

- 公開ページがWCAGを満たすことと、編集画面がATAGを満たすことは別の評価
- ATAGのPart Aは、Webベースの編集UIに対して WCAG 2.0 の達成基準を参照する
- ATAGのPart Bが言う「アクセシブルなコンテンツ」は、WCAG 2.0 の達成基準を満たすコンテンツ
- ATAG自体は WCAG の “accessibility supported” 要件を含まない。適合の文言は「WCAGに適合」ではなく「WCAGの達成基準を満たす」
- 公開後のページがWCAGに適合しているかの判定は、ツールのATAG適合とは独立

> 参照:
> - [W3C WAI — Essential Components of Web Accessibility](https://www.w3.org/WAI/fundamentals/components/)
> - [W3C — ATAG 2.0（Relationship to WCAG 2.0）](https://www.w3.org/TR/ATAG20/)

## 二つのパート

- **Part A**: 障害のある作成者が、編集UI自体を使えるようにする
- **Part B**: 障害の有無にかかわらず、どの作成者もアクセシブルなコンテンツを作りやすくする
- フォーラムやコメントのように、読む人が同時に書く場では、編集UIの問題と投稿内容の問題が同じ画面に重なる
- Part Bを満たすための検査・修復・説明UIにも、Part Aがかかる。チェック機能自体がキーボードやスクリーンリーダーで使えないと不足

> 参照: [W3C — ATAG 2.0 Introduction](https://www.w3.org/TR/ATAG20/)

## Part A — 編集UIをアクセシブルにする

| 原則 | ねらい |
|---|---|
| A.1 編集UIは適用されるガイドラインに従う | Web製UIはWCAG、非Webはプラットフォームのアクセシビリティ指針 |
| A.2 編集ビューは知覚可能 | 代替コンテンツを作成者からも分かり、表示をプログラムから解釈できる |
| A.3 編集ビューは操作可能 | キーボード、十分な時間、閃光の回避、構造による移動、検索、設定、プレビュー |
| A.4 編集ビューは理解可能 | 操作の取り消し、アクセシビリティ機能を含む説明 |

- プレビューを自前描画するなら、市販のユーザーエージェントと同等か、それ以上にアクセシブルであること（A.3.7）
- 作成操作は取り消せるか、実行前に確認を取ること（A.4.1.1、レベルA）

> 参照: [W3C WAI — ATAG at a Glance](https://www.w3.org/WAI/standards-guidelines/atag/glance/)

## Part B — アクセシブルなコンテンツ作りを支える

| 原則 | ねらい |
|---|---|
| B.1 全自動の処理はアクセシブルな出力にする | 自動生成物の達成、変換時にアクセシビリティ情報を残す |
| B.2 作成者のアクセシブルな制作を支える | 制限でWCAGを不可能にしない、案内、代替テキスト、テンプレート、部品 |
| B.3 既存コンテンツの改善を支える | 問題の検査と、直し方の提示 |
| B.4 その機能を表に出し、文書でも勧める | 初期状態でオン、スペルチェック等と同程度の目立ち、文書の良い例 |

- 同じ結果を出す操作が複数あるとき、アクセシブルになる選択肢は、ならない選択肢以上に目立たせる（B.2.2.1）
- 画像などを足せるなら、関連づいた代替テキストを作成者が編集できる（B.2.3.1）
- 代替テキストの自動修復は、ファイル名や “image” のような汎用文字列を入れず、セッション中なら採用・修正・拒否を作成者に渡す（B.2.3.2）
- テンプレートがあるなら、用途の幅に対してアクセシブルなテンプレートを用意する（B.2.4.1）
- 非アクセシブルなテンプレートも混ぜるなら、選択時に区別できる（B.2.4.2、レベルAA）
- 検査や修復の支援機能は、初期状態でオン（B.4.1.1）。オフにできるなら、問題が増え得ることを知らせる（B.4.1.3、レベルAA）
- 手動で直す手順の提示が、修復支援の最低ライン。自動修復は推奨されるが、それだけが必須ではない（B.3.2）

> 参照: [W3C — ATAG 2.0 Part B](https://www.w3.org/TR/ATAG20/)

## コードで見る違い

### 代替テキストはファイル名で埋めない

```html
<!-- 悪い例：アップロード時にファイル名をaltへ自動挿入し、編集欄がない -->
<img src="/uploads/IMG_2048.jpg" alt="IMG_2048.jpg">
```

```html
<!-- 良い例：挿入前に作成者が決める。装飾なら空のaltを明示できる -->
<figure>
  <img src="/uploads/hero.jpg" alt="受付カウンターで手続きする来館者">
  <figcaption>1階総合案内</figcaption>
</figure>

<!-- 編集UI側の最低限 -->
<label for="alt">代替テキスト</label>
<input id="alt" name="alt">
<label>
  <input type="checkbox" name="decorative">
  装飾画像（代替テキストなし）
</label>
```

- 自動候補を出す場合も、挿入前に採用・修正・拒否できること
- 装飾・不可視・CAPTCHAは、代替テキスト編集の例外になり得る（B.2.3.1の注）

### 見た目の装飾より、意味のある構造を目立たせる

```html
<!-- 悪い例：色と太字だけが主ボタンで、見出しは奥のメニュー -->
<button type="button">文字色</button>
<button type="button" hidden>見出し</button>
```

```html
<!-- 良い例：見出しが、装飾と同等以上の位置にある -->
<div role="toolbar" aria-label="書式">
  <button type="button" aria-pressed="false">見出し</button>
  <button type="button" aria-pressed="false">太字</button>
</div>
```

- 出力は `span` の見た目ではなく、`h2` などプログラムから解釈できる要素
- ツールバー自体はキーボードで届き、名前と押下状態が分かること（Part A）

### 変換で代替テキストを落とさない

```js
// 悪い例：最適化の過程で alt が消える
function toThumbnail(img) {
  return `<img src="${img.thumbSrc}">`;
}

// 良い例：非テキストを残す変換では、代替テキストも残す
function toThumbnail(img) {
  const alt = img.decorative ? "" : img.alt;
  return `<img src="${img.thumbSrc}" alt="${escapeHtml(alt)}">`;
}
```

- 構造の変換や再エンコードで、出力側に同等の仕組みがあるならアクセシビリティ情報を残す（B.1.2）
- 残せない変換（ベクターをラスターにする等）では、失われ得ることを既定で警告する選択肢がある

> 参照:
> - [W3C — ATAG 2.0 B.2.3 / B.1.2 / B.2.2](https://www.w3.org/TR/ATAG20/)
> - [W3C — Implementing ATAG 2.0](https://www.w3.org/TR/IMPLEMENTING-ATAG20/)

## 適合の読み方

- 達成基準はレベル A / AA / AAA。条件付きのものが多く、その機能がなければ「適用なし」になり得る
- レベルAは適用されるレベルAをすべて満たすこと。AAはAとAA、AAAはすべて
- 完成したツール単体の適合と、検査機能を別コンポーネントに任せる **部分適合（Process Component）** がある
- プラットフォームの制約で満たせない場合の **部分適合（Platform Limitations）** もある
- 第三者プラグインや、作成者が既定を変えた結果は、開発者が提供したツールの適合範囲外（Part Bの適用注記）
- セッション終了後にツールが自動生成するコンテンツ（サイト全体のテンプレート変更など）は、ツール側の責任
- 作成者自身の操作や、作成者が指定した外部フィードの結果までは、ツールは負わない

> 参照: [W3C — ATAG 2.0 Conformance](https://www.w3.org/TR/ATAG20/)

## フロントエンドの実務への落とし方

| 作っているもの | ATAGで先に見る箇所 |
|---|---|
| 管理画面・ブロックエディタ | Part A。キーボード、名前、取り消し、プレビュー |
| 画像・動画の挿入UI | B.2.3。代替テキストの編集と、ファイル名の自動挿入禁止 |
| テンプレート・パターン選択 | B.2.4。アクセシブルな雛形と、非対応雛形の区別 |
| 公開時の自動HTML生成 | B.1.1 / B.1.2。出力と変換で情報を落とさない |
| 入稿前チェック | B.3 と B.4。初期状態でオン、スペルチェックと同程度の位置、直し方の提示 |

- CMSの公開ページだけWCAGを見ても、入稿UIがアクセシブルなHTMLを書けない構造なら不足が再発する
- ブロックエディタの「見た目コンポーネント」は、出力HTMLのセマンティクスまでセットで設計する
- 文書やストーリーブックの例は、`div` をクリック領域にした実装ではなく、アクセシブルなマークアップを示す（B.4.2.1）

> 参照: [W3C WAI — ATAG Overview（Who ATAG is for）](https://www.w3.org/WAI/standards-guidelines/atag/)

## 関連して読むとよいテーマ

- WCAG 2.2の4原則 — Part Aが編集UIへ当てはめる達成基準の土台
- 画像のalt属性 — 代替テキストを作成者に渡すときの中身
- セマンティックHTMLの原則 — エディタ出力で落とさない構造
- キーボードナビゲーションの基本 — 編集UIの操作
- アクセシビリティ・オーバーレイの問題 — 公開後の後付けでは、入稿時の不足は埋まらない

## まとめ

- ATAG 2.0は、コンテンツを作るツール向けのW3C勧告
- Part Aは編集UIを障害のある作成者が使えるようにすること、Part Bは誰でもアクセシブルなコンテンツを作りやすくすること
- 公開ページのWCAG適合と、ツールのATAG適合は別々に見る
- 実装の要点は、キーボードで使える編集UI、代替テキストの編集、意味のある構造を目立たせること、変換で情報を残すこと、検査を初期状態でオンにすること
- 規範の参照先はWCAG 2.0。実務ではWAIの案内どおり、最新のWCAG 2を併せて使う

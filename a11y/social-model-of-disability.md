# 障害の社会モデルとWebアクセシビリティ — 個人の能力不足ではなく、環境側の障壁として捉える

## 社会モデルとは

- 障害（disability）を、個人の身体・精神の状態そのものではなく、環境や社会の側にある障壁との相互作用として捉える考え方
- 対になるのが医療モデル（個人モデル）— 「障害は個人の欠損・治療対象」と見る立場
- 社会モデルでは「使えなくしているのは階段・読めないPDF・キーボード非対応のUIなどの設計」と見る
- Webでは、同じ機能でも実装次第で障壁にもなり、参加の手段にもなる
- W3C WAIも、悪い設計が排除を生み、良い設計が障壁を取り除く、という文脈でアクセシビリティを説明する

> 参照:
> - [W3C WAI — Introduction to Web Accessibility](https://www.w3.org/WAI/fundamentals/accessibility-intro/)
> - [W3C WAI Curricula — What is Web Accessibility](https://www.w3.org/WAI/curricula/foundation-modules/what-is-web-accessibility/)

## 医療モデルと社会モデルの対比

| 観点 | 医療モデル（個人モデル） | 社会モデル |
|---|---|---|
| 問題の所在 | 個人の能力・身体・診断 | 環境・制度・設計の障壁 |
| 解決の主語 | 個人が適応・訓練・治療する | 社会・プロダクト側が障壁を取り除く |
| Webでの言い方の例 | 「スクリーンリーダーが使えない人」 | 「スクリーンリーダーで操作できないサイト」 |
| 設計への帰結 | 例外対応・後付けの救済 | 最初から多様な使い方を前提にする |
| 責任の置き方 | ユーザー側の努力不足になりやすい | 作り手・提供者側の設計責任 |

- 社会モデルは「障害の体験や医療的ニーズを否定する」ものではない
- 「誰の問題として設計を語るか」を切り替える枠組み

## Webにおける社会的障壁の例

| 環境側の障壁 | 起きること | 取り除く方向 |
|---|---|---|
| 画像に意味のある`alt`がない | 情報が伝わらない | 代替テキストを付ける |
| マウス前提のUI | キーボード・スイッチ操作ができない | フォーカス可能・キー操作可能にする |
| 色だけでの状態表示 | 色覚特性やロービジョンで判別できない | テキスト・アイコン・パターンを併用 |
| キャプションのない動画 | 音声情報が得られない | 字幕・文字起こしを用意する |
| 曖昧なエラー文 | フォームを完了できない | どこが・なぜ・どう直すかを示す |
| 時間制限のみの手続き | 読む・入力する時間が足りない | 延長・解除・十分な時間を用意する |

- 障がいはユーザーの中に固定されているのではなく、ページの設計との組み合わせで生じる
- 同じユーザーでも、アクセシブルなサイトでは障壁が小さく、非アクセシブルなサイトでは大きくなる

> 参照:
> - [W3C WAI — Diverse Abilities and Barriers](https://www.w3.org/WAI/people-use-web/abilities-barriers/)
> - [W3C WAI — How People with Disabilities Use the Web](https://www.w3.org/WAI/people-use-web/)

## なぜフロントエンドで社会モデルが効くか

- 「特殊なユーザー向けの追加作業」ではなく「環境（コード・UI）の責任」として優先度が上がる
- バグ修正と同じ感覚で扱える — 壊れているのはユーザーではなくインタフェース
- チェックリスト消化の先に、「誰が・どの操作で・どこで止まるか」を問える
- 一時的・状況的な制約（片手操作、まぶしさ、騒音）も同じ枠で説明できる
- チーム内の言い回しが変わる — 「対応が難しいユーザー」→「対応できていないUI」

## 言い換えの練習（設計レビュー用）

| 医療モデル寄りの言い方 | 社会モデル寄りの言い方 |
|---|---|
| このユーザーはサイトを使えない | このUIは一部の操作手段を想定していない |
| 障害があるから特別対応が必要 | 標準の操作経路に障壁がある |
| スクリーンリーダーユーザー向けに直す | 支援技術でも同じ情報が届くように直す |
| アクセシビリティは後で足す | 最初の設計要件に入れる |
| 例外ケース | 想定すべき利用条件のひとつ |

## コードに落とすときの視点

### 悪い例：個人の「できない」を前提にした救済

```html
<!-- マウスでしか押せない見た目だけのボタン -->
<div class="btn" onclick="submitForm()">送信</div>
<p class="note">操作できない場合は電話でお問い合わせください</p>
```

- 代替手段の案内自体は有用な場合もある
- ただし本線のUIを直せば多くの人が同じ経路で完了できるのに、最初から外へ逃がしている

### 良い例：環境側の障壁を取り除く

```html
<button type="submit">送信</button>
```

```css
.btn:focus-visible {
  outline: 2px solid #005fcc;
  outline-offset: 2px;
}
```

- ネイティブの`<button>`はキーボード・支援技術の前提が揃いやすい
- 「特別な救済ページ」より、本線を使える状態にするのが社会モデル的な打ち手

### 悪い例：色だけが障壁になる

```css
.is-error {
  border-color: red;
}
```

```html
<input class="is-error" aria-invalid="true" />
```

### 良い例：色以外の手がかりも環境に置く

```html
<label for="email">メールアドレス</label>
<input
  id="email"
  type="email"
  aria-invalid="true"
  aria-describedby="email-error"
/>
<p id="email-error">形式が正しくありません。例: name@example.com</p>
```

> 参照:
> - [WCAG 2.2 — 1.4.1 Use of Color](https://www.w3.org/WAI/WCAG22/Understanding/use-of-color.html)
> - [WCAG 2.2 — 3.3.1 Error Identification](https://www.w3.org/WAI/WCAG22/Understanding/error-identification.html)

## 日本の制度とのつながり

- 障害者差別解消法は、日常生活・社会生活を制限する「社会的障壁」の除去を軸に据える
- 事業者には、過重な負担でない範囲での合理的配慮の提供が義務（2024年4月改正法施行）
- Webの事前改善（情報アクセシビリティ向上など）は「環境の整備」として努力義務に位置づけられることが多い
- つまり「個人に我慢してもらう」のではなく「障壁を取り除く／代替手段を用意する」という制度設計
- フロントエンドのアクセシビリティ対応は、環境の整備そのものであり、個別の申し出への対応も容易にする準備になる

> 参照:
> - [障害を理由とする差別の解消の推進に関する法律（e-Gov）](https://laws.e-gov.go.jp/law/425AC0000000065)
> - [内閣府 — 改正障害者差別解消法が施行されました](https://www.cao.go.jp/press/new_wave/20240520.html)
> - [令和6年版障害者白書 — 改正障害者差別解消法の施行](https://www8.cao.go.jp/shougai/whitepaper/r06hakusho/zenbun/h2_01_01_02.html)

## 国際的な人権の文脈

- 国連の障害者権利条約（CRPD）は、情報通信技術へのアクセスを権利として位置づける
- W3C WAIも、Webへの平等なアクセスを社会参加の前提として説明する
- 社会モデルは「優しさ」や任意の品質向上だけではなく、参加の権利の話につながる

> 参照:
> - [W3C WAI — Introduction to Web Accessibility](https://www.w3.org/WAI/fundamentals/accessibility-intro/)
> - [W3C WAI — Social Factors（Business Case archive）](https://www.w3.org/WAI/business-case/archive/soc)

## 社会モデルをチームに定着させるヒント

- Issueのタイトルを「〇〇できないユーザー対応」ではなく「〇〇操作で完了できないUI」にする
- 受け入れ条件にキーボード・支援技術・十分な時間・代替テキストなどを最初から書く
- 自動テストだけでなく、実際の操作経路で「どこで止まるか」を確認する
- オーバーレイや後付けウィジェットだけで「対応済み」としない — 本線のHTML/CSS/JSを直す
- 障害のある人の参加（調査・テスト・フィードバック）を設計プロセスに入れる

> 参照:
> - [W3C WAI — Involving Users in Web Projects](https://www.w3.org/WAI/planning/involving-users/)
> - [W3C WAI — Accessibility, Usability, and Inclusion](https://www.w3.org/WAI/fundamentals/accessibility-usability-inclusion/)

## まとめ

- 社会モデルは、障害を個人の不足ではなく環境側の障壁との関係として捉える枠組み
- Webアクセシビリティは、その障壁をコードと設計で取り除く実践
- 「特別な人への救済」より「本線のUIを多様な操作手段で通せるようにする」が基本姿勢
- 日本の差別解消法も社会的障壁の除去を軸にしており、環境の整備としての対応とつながる
- チームの言葉とIssueの切り方を社会モデルに寄せると、優先度と責任の所在がはっきりする

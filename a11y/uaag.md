# UAAGについて — ブラウザなどユーザーエージェント側のガイドライン

## UAAGとは

- **UAAG** = User Agent Accessibility Guidelines（ユーザーエージェントのアクセシビリティガイドライン）
- **ユーザーエージェント**は、Webコンテンツを取得し、描画し、利用者の操作を仲介するソフトウェア
- 例: ブラウザ、ブラウザ拡張、メディアプレイヤー、リーダー。利用者の選んだWebを開くアプリも含まれ得る
- ねらいは、障害のある人を含む利用者が、Webへ入る環境側を自分で制御できること
- 文字サイズ、配色、キーボード、ページ内検索、支援技術への情報の受け渡しは、ページ本文よりブラウザ側が担う方がよいものがある
- 読む相手は、ブラウザや拡張の開発者に加え、ブラウザを選ぶ人、ベンダーへ改善を求める人
- Webアクセシビリティの構成要素では、コンテンツが WCAG、作成ツールが ATAG、利用者の環境が UAAG

> 参照:
> - [W3C WAI — UAAG Overview](https://www.w3.org/WAI/standards-guidelines/uaag/)
> - [W3C — UAAG 2.0](https://www.w3.org/TR/UAAG20/)
> - [W3C WAI — Essential Components of Web Accessibility](https://www.w3.org/WAI/fundamentals/components/)

## WCAG・ATAGとの違い

| ガイドライン | 主な対象 | 問い |
|---|---|---|
| WCAG | 公開されるWebコンテンツ | 利用者がそのページを使えるか |
| ATAG | コンテンツを作るツール | 作成者はツールを使えるか。ツールはアクセシブルな制作を支えるか |
| UAAG | ブラウザなどのユーザーエージェント | 利用者の環境側はコンテンツを届け、操作を受け渡すか |

- サイトの適合宣言に使うのは WCAG。ページが UAAG に適合する、という宣言はしない
- UAAG 2.0 の原則1〜3は WCAG 2.0 の知覚可能・操作可能・理解可能と並行。原則4と5はユーザーエージェント固有
- ブラウザの画面のうち HTML でできた部分には、UAAG 5.1.1 が WCAG 2.0 の達成基準を参照する
- WCAG の「アクセシビリティサポート」は、その技術の使い方が利用者の支援技術とユーザーエージェントで実際に使えることを求める。コンテンツの達成は、ブラウザが情報を渡せることに依存する

> 参照:
> - [W3C — UAAG 2.0（Relationship to WCAG 2.0）](https://www.w3.org/TR/UAAG20/)
> - [W3C WAI — Understanding Conformance（accessibility supported）](https://www.w3.org/WAI/WCAG22/Understanding/conformance.html)

## いまの位置づけ

- **UAAG 1.0** は W3C Recommendation（2002年12月）。勧告だが、対象ブラウザの世代が古い
- **UAAG 2.0** は W3C Working Group Note（2015年12月15日）。勧告ではない
- 勧告トラックの作業だったが、ブラウザUIの網羅的な試験資源が足りず、Candidate Recommendation の前に閉じた
- 機能の約90%には実装候補が見つかっている。正式な試験はされていない。実装が見つからなかった項目は、プラットフォームの文字設定を既定にする 1.4.5、順送りの周回を選ぶ 2.2.4、フォーム送信前の確認 3.1.6
- 作業グループ（UAWG）は2016年1月に終了。W3Cは UAAG 2.0 を勧告へ進める予定はない
- WAIの概要（2024年5月更新）は、なお UAAG 2.0 を使うよう勧めている。ブラウザ間でアクセシビリティ機能の対応が揃っていない、という理由
- ユーザーエージェント側の考慮は、将来のアクセシビリティガイドラインへ取り込む方針。2026年10月時点の足場は、コンテンツについては WCAG 2.2、環境側の参照資料としては UAAG 2.0

> 参照:
> - [W3C WAI — UAAG Overview（UAAG 2.0）](https://www.w3.org/WAI/standards-guidelines/uaag/)
> - [W3C — UAAG 2.0 Status](https://www.w3.org/TR/UAAG20/)

## 五つの原則

| 原則 | ブラウザ側の仕事 | コンテンツ側が残すもの |
|---|---|---|
| 1. 知覚可能 | 代替コンテンツ、文字設定、ズーム、選択とフォーカスの強調 | 認識できる代替テキスト、見出し、本文の文字 |
| 2. 操作可能 | キーボード、順送り、ページ内検索、見出し移動、時間のかかる操作 | ネイティブの操作対象。フォーカスを閉じ込めない構造 |
| 3. 理解可能 | 利用者の依頼なしにフォーカスを変えない。機能の説明 | 予期しない遷移を起こさない操作 |
| 4. プログラムからのアクセス | 名前・役割・状態・値・フォーカスをプラットフォームのアクセシビリティAPIへ渡す | ブラウザが読める要素と、必要なARIA |
| 5. 仕様と慣例 | コンテンツ仕様のアクセシビリティ機能と、OSのUI慣例を実装する | その機能（`alt`、見出し、キャプション）を実際に書く |

- 達成基準はレベル A / AA / AAA。Aは適用されるAのすべて、AAはAとAA、AAAはすべて
- 多くの必須動作は、利用者が設定で選べる形でもよい。達成基準が既定と書いていない限り、最初からオンである必要はない
- ブラウザ自身がすべて実装しなくてよい。OSや、発見できて追加費用なく入れられる拡張でも満たせる
- 適用は、取得済みで、隠されておらず、ブラウザが認識できるコンテンツに限る。認識できない描画には、検索も見出し移動も届かない

> 参照: [W3C — UAAG 2.0 Guidelines](https://www.w3.org/TR/UAAG20/)

## コードで見る「ブラウザの仕事を潰す」

UAAGの適合主体はブラウザである。次の例は、制作者の指定が、ブラウザが提供する拡大・フォーカス・キーボード・検索を止める箇所。

### 拡大の上限を作者が閉じない

UAAG 1.8.5（レベルA）は、トップレベルの表示を既定の500%以上まで拡大し、10%以下まで縮小できることをユーザーエージェントに求める。WCAG 2.2 の 1.4.4（テキストのサイズ変更、AA）は、コンテンツが支援技術なしで200%まで拡大できることを求める。数字の主体が違う。

```html
<!-- 悪い例：ピンチ拡大を止める指示をブラウザへ出す -->
<meta name="viewport" content="width=device-width, initial-scale=1, maximum-scale=1, user-scalable=no">
```

```html
<!-- 良い例：幅だけを端末に合わせ、拡大は利用者が決める -->
<meta name="viewport" content="width=device-width, initial-scale=1">
```

- デスクトップのブラウザは、この `meta` を拡大の禁止として使わない
- iOSのSafariは iOS 10 以降、`user-scalable=no` と極端な `maximum-scale` を既定で無視する
- AndroidのChromeでは、既定のままだと `maximum-scale=1` がピンチ拡大を止める、という2025年の確認がある。アクセシビリティ設定で上書きできるが、最初から拡大できる状態とは別
- 要素単位では `touch-action: pan-y` だけにすると、その範囲のピンチ拡大が外れる。縦スクロールと拡大を両立するなら `pan-y pinch-zoom` を指定する

> 参照:
> - [W3C — UAAG 2.0 1.8.5](https://www.w3.org/TR/UAAG20/#sc_185)
> - [MDN — viewport](https://developer.mozilla.org/ja/docs/Web/HTML/Reference/Elements/meta/name/viewport)
> - [W3C WAI — Understanding Resize Text](https://www.w3.org/WAI/WCAG22/Understanding/resize-text.html)

### フォーカスの強調を作者が消さない

UAAG 1.3.1（レベルA）は、キーボードフォーカス、選択、ページ内検索の一致、訪問済みと未訪問のリンクを、作者の指定より優先して区別できるようにすることを求める。

```css
/* 悪い例：ブラウザが描くフォーカスを消す */
:focus {
  outline: none;
}
```

```css
/* 良い例：マウス操作では抑え、キーボードでは輪郭を残す */
:focus {
  outline: none;
}

:focus-visible {
  outline: 3px solid #0b57d0;
  outline-offset: 2px;
}
```

- ブラウザが作者のCSSを上書きする設定を、すべての利用者がオンにしているわけではない
- 見えるフォーカス自体は WCAG 2.2 の 2.4.7（AA）がコンテンツ側に求める。UAAGは、その強調を利用者の設定でさらに変えられることをブラウザに求める

> 参照:
> - [W3C — UAAG 2.0 1.3.1](https://www.w3.org/TR/UAAG20/#sc_131)
> - [W3C WAI — Understanding Focus Visible](https://www.w3.org/WAI/WCAG22/Understanding/focus-visible.html)

### ネイティブの操作はブラウザに任せる

UAAG 2.1.1 と 2.2.1（いずれもレベルA）は、機能をキーボードで操作でき、有効な要素を順にフォーカス移動できることを求める。4.1.2（レベルA）は、名前・役割・状態・値・フォーカスをアクセシビリティAPIへ渡すことを求める。`button` や `a` ではブラウザがこれを行う。

```html
<!-- 悪い例：クリック以外の経路と、名前・役割の公開がブラウザに発生しない -->
<div class="button" onclick="location.href='/apply'">申し込む</div>
```

```html
<!-- 良い例：Tab、Enter、役割はユーザーエージェントが担う -->
<a href="/apply">申し込む</a>
```

- `div` にキーボードと ARIA を後から足すのは、ブラウザがすでに持つ動作の再実装
- カスタムのコンボボックスやタブを作るときは、順送り、選択と実行の分離、名前・役割・状態を、ネイティブ相当まで自分で渡す

### 選択と実行を分ける

UAAG 2.1.4（レベルA）は、フォーカスや選択の移動だけでは、作者のコンテンツが状態やフォーカスをさらに変えないよう、利用者が指定できることを求める。

```html
<!-- 悪い例：矢印キーで項目が変わった瞬間に遷移する -->
<label for="section">セクション</label>
<select id="section" onchange="location.href=this.value">
  <option value="/guide">ガイド</option>
  <option value="/price">料金</option>
</select>
```

```html
<!-- 良い例：選ぶ操作と、移動する操作が別 -->
<form action="/go" method="get">
  <label for="section">セクション</label>
  <select id="section" name="to">
    <option value="guide">ガイド</option>
    <option value="price">料金</option>
  </select>
  <button type="submit">移動</button>
</form>
```

- ネイティブの `select` は、矢印キーでは値の選択にとどまり、フォームの送信は別操作
- カスタムリストで矢印キーと同時にページ遷移させると、キーボード利用者が途中の項目を確認できない

> 参照: [W3C — UAAG 2.0 2.1.4](https://www.w3.org/TR/UAAG20/#sc_214)

### 検索と見出し移動が認識できる文字を残す

UAAG 2.4.1（レベルA）は描画された文字のページ内検索、2.5.1（レベルAA）は見出し・セクション・表の中の構造移動を求める。適用注記により、ブラウザが認識できない内容は対象外になる。

```html
<!-- 悪い例：ピクセルになった文字は検索も見出しジャンプもできない -->
<canvas id="hero" width="800" height="200"></canvas>
```

```html
<!-- 良い例：見えるタイトルはHTMLの見出し -->
<h1>料金プラン</h1>
<img src="/chart.png" alt="個人プランは月額980円、団体プランは月額2400円">
```

- 代替テキストが空や欠落のとき、ブラウザはファイル名で穴埋めしない（1.2.1、レベルAA）。欠落を支援技術が検知できるようにするため
- 制作者がファイル名を `alt` に書くと、欠落ではなく「代替がある」状態になる。穴埋め禁止の意味が消える

> 参照:
> - [W3C — UAAG 2.0 2.4.1 / 2.5.1 / 1.2.1](https://www.w3.org/TR/UAAG20/)

## 自作アプリはユーザーエージェントか

- 利用者が選んだ任意のWebを取得して描画し、操作させるアプリは、単独のユーザーエージェントとして扱う
- 開発者が決めた限られたコンテンツだけを描くアプリは、ユーザーエージェントではない場合がある
- どちらでも、中のWebコンテンツには WCAG がかかる
- ユーザーエージェントではないアプリの開発者は、WCAG を超える UAAG の要求までは負わない、と UAAG 2.0 は説明している
- アプリ内ブラウザや、任意のURLを開く WebView は前者に寄りやすい。自社サイトを包んだだけのシェルは後者に寄りやすい

> 参照: [W3C — UAAG 2.0（Relationship to WCAG 2.0）](https://www.w3.org/TR/UAAG20/)

## フロントエンドの実務への落とし方

| 作っているもの | 見ること |
|---|---|
| 通常のWebページ | 適合の宣言は WCAG。拡大禁止、フォーカス消去、クリックだけの `div` でブラウザの動作を潰さない |
| カスタムウィジェット | キーボード、選択と実行の分離、名前・役割・状態を、ネイティブ相当まで渡す |
| 見出し・表・代替テキスト | ブラウザと支援技術が認識できる構造として残す |
| 任意のWebを開くアプリ内ブラウザ | ユーザーエージェントに当たり得る。UAAGをブラウザ側の要件として読む |
| 自社画面だけを包むアプリ | 中身の判定は WCAG。UAAGの全達成基準をそのアプリの適合目標にしない |

- ページ内検索、文字の拡大、フォーカスリング、アクセシビリティAPIは、まずブラウザの機能として期待する
- その機能が認識できるのは、HTMLとして存在する文字とコントロール
- UAAG 2.0 は勧告ではない。ブラウザ選定や不具合報告の参照には使い、サイトの適合レベルとしては使わない

> 参照: [W3C WAI — UAAG Overview（Who UAAG is for）](https://www.w3.org/WAI/standards-guidelines/uaag/)

## 関連して読むとよいテーマ

- ATAG 2.0について — 作成ツール側。UAAGと対になるWAIのガイドライン
- WCAG 2.2の4原則 — コンテンツ側の知覚可能・操作可能・理解可能・堅牢
- アクセシビリティツリーの仕組み — 原則4が支援技術へ渡す名前・役割・状態
- キーボードナビゲーションの基本 — ブラウザがネイティブ要素に付ける操作
- フォーカスインジケーターのカスタマイズ — 作者が輪郭を残すときの実装
- セマンティックHTMLの原則 — 検索と見出し移動が認識できるマークアップ

## まとめ

- UAAGは、ブラウザやメディアプレイヤーなど、Webを描画して操作を仲介するソフトウェア向けのガイドライン
- 現行の参照は UAAG 2.0（2015年の Working Group Note）。勧告ではなく、サイトの適合宣言には使わない
- 原則1〜3は WCAG と並行し、原則4は支援技術への公開、原則5は仕様とOSの慣例
- ページ側の仕事は、拡大・フォーカス・キーボード・検索が届くよう、認識できるHTMLを残すこと
- 任意のWebを開くアプリはユーザーエージェントに当たり得る。決まった画面だけを出すアプリの中身は WCAG で見る

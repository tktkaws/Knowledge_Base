# VPATについて — 製品のアクセシビリティ適合を報告する書式

## VPATとは

VPAT（Voluntary Product Accessibility Template）は、ICT製品やサービスがアクセシビリティ要件をどの程度満たすか、要件ごとに記録するためのテンプレート。米国の業界団体Information Technology Industry Council（ITI）が提供している。

VPATは未記入の書式であり、特定の製品を評価して記入した完成文書を **ACR（Accessibility Conformance Report）** と呼ぶ。

| 用語 | 意味 |
|---|---|
| VPAT | ITIが提供する未記入のテンプレート |
| ACR | 製品の評価結果をVPATへ記入した適合報告書 |
| 適合基準 | WCAG、Revised Section 508、EN 301 549など、評価に使う要件 |

日常会話では「製品のVPATを提出する」と言うことが多いが、提出するのは通常、記入済みのACRである。

VPATについて最初に押さえる点は次のとおり。

- VPAT自体は試験ツールではない。製品を評価した後に結果を書く書式
- ACRを作るだけで製品がアクセシブルになるわけではない
- **VPAT認証**という制度はない
- ITIが個々のACRを審査、承認する仕組みではない
- 第三者監査は必須ではないが、調達条件で要求される場合がある
- ACRに一つでも不適合があるから提出できない、という書式ではない
- `Supports`の数を合計して合否を出す採点表ではない

ITIによると、製品所有者が完成したACRを顧客へ提供したり、自社サイトで公開したりできるが、ITIへ提出して認証ロゴを得る手続きはない。

> 参照:
> - [ITI — VPAT](https://www.itic.org/policy/accessibility/vpat)
> - [Section508.gov — ACR/VPAT FAQ](https://www.section508.gov/sell/acr-vpat-faq/)

## 何のために使うのか

ACRは、主に発注者が複数のICT製品を比較し、アクセシビリティ上の特徴と障壁を確認するために使う。

```text
製品の範囲を決める
        ↓
適用する基準を決める
        ↓
自動・手動・支援技術で評価する
        ↓
試験記録を要件ごとに整理する
        ↓
VPATへ記入してACRにする
        ↓
発注者が業務要件と照らして確認する
```

米国連邦政府の調達では、連邦機関が候補製品のSection 508対応を評価する資料としてACRを要求することがある。VPATという特定書式を法律が直接義務付ける構造ではないが、募集・契約条件でACRの提出が必須になれば、ベンダーはその条件に従う。

Section508.govは、製品が完全適合していない場合もACRを作成し、既知の不適合を報告するよう案内している。正確な不適合情報があれば、発注者は利用者への影響、代替手段、他製品との差を判断できる。

> 参照:
> - [Section508.gov — Accessibility Conformance Report](https://www.section508.gov/sell/acr/)
> - [Section508.gov — Request Accessibility Information from Vendors & Contractors](https://www.section508.gov/buy/request-accessibility-information/)

## 最新版と四つのEdition

2026年11月17日時点で、ITIが公開する最新版は **VPAT 2.5Rev（2025年4月）**。四つのEditionがある。

| Edition | 含む主な基準 | 主な用途 |
|---|---|---|
| 508 | Revised Section 508、そこから参照されるWCAG 2.0 | 米国連邦政府向け |
| EU | EN 301 549、そこから参照されるWCAG 2.1 | 欧州市場・欧州調達向け |
| WCAG | WCAG 2.0、2.1、2.2 | WCAGを中心に報告する場合 |
| INT | 508、EU、WCAGの内容 | 複数市場を一つの報告で扱う場合 |

Edition名が違えば、表の行と参照するWCAGの版も変わる。単に「VPAT 2.5を使う」と決めず、次を確認する。

1. 誰へ提出するか
2. 調達文書が指定する規格、版、Editionは何か
3. 対象製品がWeb、ソフトウェア、文書、ハードウェア、サポートのどれを含むか
4. 一つの市場だけか、複数市場へ同じ報告を出すか
5. 追加資料や第三者評価が要求されているか

米国連邦政府向けなら、Revised Section 508を含む508 EditionまたはINT Editionを選ぶ。WCAG 2.2への対応も報告したいだけなら、調達先の要求を確認せず508 EditionをWCAG Editionへ置き換えない。508 Editionが含むSection 508固有のソフトウェア、ハードウェア、サポート要件が欠けるためである。

INT Editionは一つの文書で複数規格を扱えるが、分量とレビュー対象が大きくなる。提出先が一つの規格だけを求めるなら、対象を絞ったEditionの方が読みやすい場合がある。

ITIはテンプレートを無料で提供しているが、VPATの名称と書式は登録サービスマーク。テンプレートの指示を読み、無断で書式を変更せずに使う。

> 参照: [ITI — VPAT 2.5Rev editions](https://www.itic.org/policy/accessibility/vpat)

## ACR作成の全体像

| 段階 | 行うこと | 主な成果物 |
|---|---|---|
| 1. 要求確認 | 提出先、Edition、規格、期限、第三者評価の要否を確認 | 要求事項一覧 |
| 2. 範囲決定 | 製品版、構成、機能、プラットフォーム、除外範囲を固定 | 評価スコープ |
| 3. 適用判断 | 製品に関係する表と要件を選ぶ | 適用要件一覧 |
| 4. 評価計画 | 主要タスク、試験方法、環境、担当者を決める | テスト計画 |
| 5. 製品評価 | 自動、手動、キーボード、支援技術などで確認 | 試験記録・課題一覧 |
| 6. ACR記入 | 適合レベルと具体的な根拠を書く | ACR草案 |
| 7. レビュー | 技術、法務・調達、製品担当で整合を確認 | 承認済みACR |
| 8. 公開・更新 | アクセシブルな形式で提供し、変更時に再評価 | 公開版・更新記録 |

営業担当が受注直前に推測で埋める文書にしない。ACRの各行を、再現可能な試験記録と結び付ける。

## 最初に製品の範囲を固定する

同じ製品名でも、版、契約プラン、設定、OS、ブラウザによって機能とアクセシビリティが変わる。表を書く前に、何を評価した報告書かを固定する。

```md
## 評価対象

- 製品名: Example Cloud Admin
- 製品版: 2026.11.2
- 評価ビルド: web-20261112.3
- 対象プラン: Enterprise
- 対象機能: ログイン、利用者管理、請求、レポート出力、ヘルプ
- 対象言語: 日本語、英語
- 対象環境: Windows 11 / Chrome、macOS / Safari
- 対象外: ベータ版AIアシスタント、販売代理店が追加する外部プラグイン
- 評価期間: 2026年10月20日〜11月12日
```

対象外を自由に決めて不適合を隠してはいけない。利用者が製品の主要タスクで必ず通る認証、決済、外部ID連携などは、自社が作った画面でなくても実利用上の範囲として扱う。

### 製品を分けた方がよい場合

- Web版とデスクトップ版でUIと対応状況が大きく異なる
- 管理者画面と一般利用者画面で対象者、機能、更新周期が異なる
- 無料版と有料版で主要機能が異なる
- OEM製品を大幅に設定変更して提供する
- 一つの文書ではRemarks and Explanationsが読みにくくなる

一つのACRにまとめる場合は、各行でプラットフォーム別の結果を区別する。最も良い環境だけを代表値にしない。

## 製品を評価してから書く

VPATの行を見ながら印象で`Supports`を選ばない。先に評価計画を作り、製品を試験する。

### 評価に含める方法

- HTML、ARIA、色、名前・役割・値などの自動検査
- キーボードだけでの主要タスク確認
- 200%・400%拡大とリフロー
- 色と非テキストコントラストの測定
- スクリーンリーダーによる操作と読み上げ確認
- 音声入力、スイッチ、画面拡大など、製品に応じた支援技術
- PDF、動画、生成文書、通知メールなどWeb画面以外の確認
- エラー、空状態、タイムアウト、権限差など状態別の確認
- 障害のある利用者による主要タスクの利用テスト

自動ツールだけでは、フォーカス順序、意味の分かるラベル、エラーからの回復、スクリーンリーダーでの実用性などを判断できない。

### 評価環境を記録する

```md
## Evaluation Methods Used

- axe-core 4.xによる自動検査
- HTML Validatorによるマークアップ確認
- Windows 11、Chrome、Firefoxでのキーボード操作
- NVDA、Chromeによる主要タスクの確認
- macOS、Safari、VoiceOverによる主要タスクの確認
- 400%拡大、幅320 CSS px相当でのリフロー確認
- カラーコントラストの手動測定
- 主要タスク: ログイン、利用者追加、請求書確認、CSV/PDF出力
- 評価対象ビルド: web-20261112.3
```

実際の報告では、ツール、ブラウザ、OS、支援技術の版も残す。単に「自動・手動テストを実施」と書くより、発注者が評価の深さと再現条件を判断しやすい。

## 表紙情報を書く

VPAT 2.5Revには、製品と評価の前提を示す欄がある。

| 項目 | 書く内容 |
|---|---|
| Name of Product/Version | 製品名と、結果が有効な版 |
| Report Date | ACRを発行した年月日 |
| Product Description | 製品の目的、利用者、主な機能、構成 |
| Contact Information | 内容を説明できる窓口 |
| Notes | 対象範囲、対象外、前提、用語、既知の制約 |
| Evaluation Methods Used | 試験方法、環境、ツール、支援技術、主要タスク |
| Applicable Standards/Guidelines | このACRで扱う規格と版 |

製品説明をマーケティング文だけにしない。「クラウドで業務を革新するプラットフォーム」では、何を評価したか分からない。

```md
Product Description:
ブラウザで利用する人事管理SaaS。従業員情報の検索・編集、
休暇申請、承認、CSV/PDFレポート出力、管理者向け設定を含む。
このACRはEnterpriseプランのWebアプリと利用者向けヘルプを対象とする。
```

ACRの発行者と第三者評価者が異なる場合は、誰が試験し、誰が内容に責任を持つかも分かるようにする。

> 参照: [Section508.gov — How to Create an ACR with a VPAT](https://www.section508.gov/sell/how-to-create-acr-with-vpat/)

## 三つの列を理解する

VPATの主要な表は三つの列からなる。

| 列 | 内容 |
|---|---|
| Criteria | WCAG達成基準や規格の条項 |
| Conformance Level | 定められた用語による適合状況 |
| Remarks and Explanations | 判定の根拠、対象、既知の例外、影響 |

Conformance Levelには、テンプレートが定める表記を使う。

| 表記 | VPATでの意味 |
|---|---|
| Supports | 少なくとも一つの方法で要件を満たし、既知の不適合がない、または同等の代替方法で満たす |
| Partially Supports | 製品の一部の機能が要件を満たさない |
| Does Not Support | 製品機能の大部分が要件を満たさない |
| Not Applicable | その要件が製品に関係しない |

古いACRで使われる`Supports with Exceptions`は、現在のテンプレートでは`Partially Supports`に置き換えられている。独自に`Mostly Supports`、`Compliant`、`Pass`などを作らない。

`Not Evaluated`は、評価していないA・AA要件を埋めるための表記ではない。Section508.govの作成案内では、任意のレベルAAA表だけで使用できるとしている。評価していない必須行を`Not Applicable`へ置き換えない。

### WCAGの適合と行ごとの表記を混同しない

一つの達成基準に`Partially Supports`があれば、その製品範囲がWCAGの当該レベルへ完全適合しているとは言えない。ACRの行ごとの状況と、「製品全体がWCAG AA適合」という表明を分ける。

また、ACRは単純な多数決ではない。ほとんどの行が`Supports`でも、ログインや購入を完了できない一つの障壁が利用者には重大になる。

## Remarks and Explanationsを具体的に書く

Remarks and Explanationsは、発注者が製品の状態を判断する中心部分。`Partially Supports`と`Does Not Support`では説明が必要で、`Supports`でも根拠を書くことが推奨される。

次の要素を組み合わせる。

```text
対象機能・環境
  + 確認した実装または操作
  + 判定の根拠
  + 既知の例外
  + 利用者への影響
  + 利用できる回避策
```

### `Supports`の例

| Criteria | Conformance Level | Remarks and Explanations |
|---|---|---|
| 1.1.1 Non-text Content | Supports | Webアプリ内の情報画像には代替テキストがあり、装飾画像は空のalt属性またはCSS背景として実装している。主要画面を自動検査とNVDA・VoiceOverで確認した。 |

「準拠しています」「対応済みです」だけでは、対象も根拠も分からない。

### `Partially Supports`の例

| Criteria | Conformance Level | Remarks and Explanations |
|---|---|---|
| 2.1.1 Keyboard | Partially Supports | 主要なフォームとナビゲーションはキーボードで操作できる。管理者画面の列並べ替えはドラッグ操作しかなく、キーボードから実行できない。列見出しのメニューから並べ替える代替操作を次期リリースで提供予定。 |

「一部を除き対応」のような説明ではなく、どの機能が、どう使えず、代替手段があるかを書く。修正予定を書く場合も、現在の判定を将来予定で良く見せない。

### `Does Not Support`の例

| Criteria | Conformance Level | Remarks and Explanations |
|---|---|---|
| 1.2.2 Captions (Prerecorded) | Does Not Support | 製品内の操作説明動画12本に同期したキャプションがない。テキスト版マニュアルは利用できるが、動画内のすべての音声情報を同等には提供していない。 |

不適合を隠さず、対象件数や範囲を示す。回避策があっても、要件を満たしていなければ`Supports`にはしない。

### `Not Applicable`の例

| Criteria | Conformance Level | Remarks and Explanations |
|---|---|---|
| 1.2.4 Captions (Live) | Not Applicable | 製品はライブ音声・映像コンテンツを提供しない。録画済みの操作説明動画は1.2.2で報告する。 |

`Not Applicable`には、なぜ対象外かを書く。「対象外」の一語だけでは、適用判断をしたのか、評価を省略したのか区別できない。

## 複数環境の差を一つの行に書く

同じ達成基準でも、Web版とデスクトップ版、WindowsとmacOSで結果が異なることがある。

```text
Partially Supports

Web版:
キーボードで全機能を操作できる。

Windowsデスクトップ版 6.2:
レポート一覧の行メニューをキーボードで開けない。

macOSデスクトップ版 6.2:
Web版と同等に操作できる。
```

総合判定を最良の環境へ合わせず、既知の不適合があるなら`Partially Supports`として環境別に説明する。差が多い場合はACRを分ける。

## 表ごとの適用範囲を判断する

508 EditionにはWCAG表だけでなく、Revised Section 508の章が含まれる。製品の構成に応じて記入する。

| 製品の内容 | 主に確認する表 |
|---|---|
| Webコンテンツ | WCAGレベルA・AA |
| 電子文書 | WCAGレベルA・AAと文書に関係する要件 |
| ソフトウェア | WCAGレベルA・AA、Chapter 5 Software |
| ハードウェア | Chapter 4 Hardware |
| サポート文書・サービス | Chapter 6 Support Documentation and Services |
| 技術要件だけで扱えない機能 | Chapter 3 Functional Performance Criteria |
| オーサリングツール | 生成コンテンツとオーサリング機能の要件 |

SaaSにPDFマニュアルと問い合わせ窓口が付くなら、Web画面だけを評価して終わらない。ソフトウェア、生成する文書、ヘルプ、サポートなど、製品として提供する範囲を見る。

表全体が適用されない場合は、その表のNotes欄へ理由を書く。空欄のまま削除すると、意図的に対象外としたのか記入漏れか分からない。

## 試験記録とACRを対応付ける

ACRは要約文書であり、すべての不具合詳細を一つのセルへ詰め込む場所ではない。社内では、各判定を試験記録へたどれるようにする。

| 管理項目 | 例 |
|---|---|
| 基準 | WCAG 2.2 SC 2.4.7 |
| 対象 | 請求書一覧、行アクションメニュー |
| 環境 | Windows 11、Chrome、NVDA |
| 結果 | キーボードフォーカスの外観が表示されない |
| 利用者影響 | 現在位置を視覚的に判断できない |
| 課題ID | A11Y-284 |
| ACR判定 | Partially Supports |
| 再試験 | 2026-11-10、未修正 |

公開ACRへ内部チケットURLや個人情報を載せる必要はない。外部向けの説明と、社内で再現できる証拠を分けて管理する。

Section508.govは、ACRを補う資料として評価方法を詳しく示すSupplemental Accessibility Reportや、不適合の深刻度と利用者影響を示すIssue Detail Supplementも案内している。募集要項が求める資料を確認する。

> 参照: [Section508.gov — Request Accessibility Information](https://www.section508.gov/buy/request-accessibility-information/)

## ACR自体をアクセシブルにする

アクセシビリティ報告書が、スクリーンリーダーやキーボードで読めない状態を避ける。

### Word文書

- 組み込みの見出しスタイルを順序どおりに使う
- 表に見出し行を設定し、ページをまたぐ場合は繰り返す
- セル結合や空白だけの行で見た目を整えない
- リンクテキストから行き先が分かるようにする
- 画像に代替テキストを付ける
- 文書の言語と部分言語を設定する
- 色だけで状態を示さない
- Wordのアクセシビリティチェックだけで完了としない

### PDFで公開する場合

- Wordからタグ付きPDFとして書き出す
- 見出し、段落、リスト、表のタグを確認する
- 読み上げ順序を確認する
- 文書タイトルと言語を設定する
- キーボードでリンクを利用できることを確認する
- コピーしただけの画像PDFにしない
- 元のWordだけでなく、最終PDFもスクリーンリーダーで確認する

Section508.govの作成案内は、完成版からテンプレート冒頭の記入指示ページを除き、最終ACRそのものをアクセシブルにするよう求めている。提出先の指示とITIテンプレートのEssential Requirementsにも従う。

## 完成前に複数の役割でレビューする

| 役割 | 主な確認 |
|---|---|
| アクセシビリティ担当 | 判定と試験証拠が基準に合うか |
| 開発・QA | 製品版、再現条件、既知の不具合が正しいか |
| プロダクト担当 | 対象機能、プラン、公開予定と矛盾しないか |
| 法務・調達担当 | 契約要求、表現、商標、公開範囲が適切か |
| サポート担当 | 回避策と問い合わせ先が実際に利用できるか |
| 文書担当 | Word・PDF自体がアクセシブルか |

レビューでは、課題管理表とACRの矛盾も確認する。重大なキーボード不具合が未修正なのに2.1.1が`Supports`なら、どちらかが誤っている。

第三者が作成した場合も、製品所有者は対象版と記載内容を確認する。第三者の名前があること自体を認証のように扱わない。

## 公開と更新

ACRには、製品版と発行日を分かりやすく表示する。Webページから提供する場合は、リンク名にも製品と版を含める。

```html
<a href="/accessibility/example-cloud-admin-2026-11-acr.pdf">
  Example Cloud Admin 2026.11 アクセシビリティ適合報告書（PDF）
</a>
```

「VPATはこちら」だけでは、複数製品や過去版を区別しにくい。ファイル形式も伝える。

### 更新を検討する契機

- メジャー・マイナーリリースでUIや主要タスクが変わった
- アクセシビリティ不具合を修正した
- 新しいOS、ブラウザ、支援技術へ対応した
- サードパーティ製コンポーネントを変更した
- 新しい文書、動画、モバイルアプリを追加した
- 参照規格またはVPATテンプレートが更新された
- 契約プランや既定設定が変わった
- 公開ACRと現行製品の差が大きくなった

小さな修正でも影響を確認し、必要ならACRを更新する。古いACRを残す場合は、現行版と過去版を明確に区別する。

```text
製品リリース
    ↓
アクセシビリティ影響を確認
    ├─ 影響なし → 根拠と確認日を記録
    └─ 影響あり → 関連基準を再試験
                    ↓
                 ACRを更新
```

> 参照: [Section508.gov — ACR/VPAT FAQ（製品更新時の再評価）](https://www.section508.gov/sell/acr-vpat-faq/)

## 発注者としてACRを読む

表紙から順番に、次を確認する。

1. 求めた製品、版、プランのACRか
2. 必要な規格とEditionを含むか
3. 発行日が現行製品に対して古すぎないか
4. 主要機能とサードパーティ部分が評価範囲に入っているか
5. 自動検査だけでなく手動・支援技術試験を行っているか
6. `Partially Supports`と`Does Not Support`の影響が具体的か
7. `Not Applicable`に妥当な理由があるか
8. 自組織の主要タスクを止める障壁がないか
9. 回避策を実際の利用者が使用できるか
10. デモ、試用版、追加試験で記載を検証できるか

### 注意したいACR

- 製品名だけで、版や対象プランがない
- Evaluation Methods Usedが空欄、または「自動ツール」の一語だけ
- すべての行が`Supports`で、Remarksが同じ定型文
- `Partially Supports`なのに対象機能と利用者影響がない
- 多数の`Not Applicable`に理由がない
- A・AAの必須行が`Not Evaluated`または空欄
- 現行製品より何年も前のACR
- ベータ版や限定機能だけを評価している
- 「ロードマップで対応予定」を現在の適合として数えている
- 文書自体が画像PDFで、表を読み上げられない

ACRだけで購入判断を完結させない。発注者は、自組織の重要な利用シナリオについてデモ、キーボード操作、支援技術試験、障害のある利用者による確認を組み合わせる。

`Supports`の行数が多い製品より、業務に不可欠なタスクを完了でき、既知の障壁と改善計画を正確に説明する製品の方が適切な場合がある。

## よくある失敗

### VPATとACRを同じ意味で使う

未記入の書式がVPAT、製品の結果を記入した文書がACR。ファイル名や公開ページでも区別する。

### 製品を試験せず、開発者へ口頭確認して埋める

自動、手動、支援技術の試験記録から判定する。実装意図ではなく、利用者が使う製品の結果を書く。

### Editionを提出先ではなく使いやすさで選ぶ

調達文書と対象市場を先に確認する。米国連邦向けでSection 508の表がないWCAG Editionだけを出さない。

### 不適合があるためACRを作らない

既知の不適合を具体的に書く。発注者は、影響と代替手段を含めて候補製品を比較する。

### `Supports`へ修正予定を含める

判定は発行時点の対象版に基づく。将来の計画はRemarksや別の改善計画に書き、現在の結果と分ける。

### `Not Applicable`を未試験の意味で使う

適用されない根拠を書く。未試験の必須要件を対象外として処理しない。

### 自社が作っていない画面を除外する

認証、決済、チャットなど、製品の主要タスクに組み込んだ部分は利用者にとって同じ体験。契約と技術の責任分担を整理し、評価範囲を明記する。

### 自動検査だけで完成させる

キーボード、フォーカス、読み上げ、拡大、エラー回復、主要タスクを手動で確認する。

### ACRを一度作って更新しない

製品変更とアクセシビリティ課題の修正を更新契機にする。公開版と対象製品の対応表を管理する。

### ACR自体がアクセシブルでない

最終Word・PDFの見出し、表、読み上げ順序、リンク、言語を確認する。

## 作成時のチェックリスト

### 要求と版

- [ ] 提出先と調達文書の要求を確認した
- [ ] 最新のITI公式テンプレートを確認した
- [ ] 508、EU、WCAG、INTから適切なEditionを選んだ
- [ ] Editionが参照するWCAGの版を確認した
- [ ] 第三者評価や追加資料の要否を確認した
- [ ] ITIテンプレートのEssential Requirementsを読んだ

### 評価範囲

- [ ] 製品名、版、ビルド、プランを固定した
- [ ] 対象機能、言語、プラットフォームを記録した
- [ ] Web、ソフトウェア、文書、動画、ハードウェア、サポートを整理した
- [ ] サードパーティ機能を含む主要タスクを確認した
- [ ] 対象外の範囲と理由を明記した
- [ ] 複数製品を一つのACRへまとめる妥当性を確認した

### 評価方法

- [ ] 適用する規格と要件を特定した
- [ ] 自動検査と手動検査を組み合わせた
- [ ] キーボードだけで主要タスクを確認した
- [ ] 対象ブラウザ、OS、支援技術で確認した
- [ ] 拡大、リフロー、コントラストを確認した
- [ ] エラーや権限差など複数の状態を確認した
- [ ] ツールと環境の版を記録した
- [ ] 各結果を課題・試験記録へたどれるようにした

### ACRの記入

- [ ] 表紙の製品情報と連絡先を記入した
- [ ] Evaluation Methods Usedを具体的に書いた
- [ ] 適用する表をすべて記入した
- [ ] Conformance Levelに定められた用語だけを使った
- [ ] `Partially Supports`と`Does Not Support`へ具体的な説明を書いた
- [ ] `Not Applicable`へ適用されない理由を書いた
- [ ] `Supports`にも可能な範囲で根拠を書いた
- [ ] 将来の修正予定と現在の結果を分けた
- [ ] プラットフォーム別の差を明記した
- [ ] 空欄や未評価の必須行がない

### レビューと公開

- [ ] 製品版と課題管理表の内容がACRと一致する
- [ ] 技術、製品、法務・調達、文書担当が確認した
- [ ] 指示ページを完成版から除くなど提出要領に従った
- [ ] WordまたはPDF自体のアクセシビリティを確認した
- [ ] ファイル名とリンク名から製品・版・形式が分かる
- [ ] 現行版と過去版を区別して公開した
- [ ] 更新責任者と再評価の契機を決めた
- [ ] 問い合わせ先が実際に対応できる

## まとめ

- VPATは未記入のテンプレートで、製品の評価結果を記入した完成文書がACR
- VPAT認証やITIへの提出・承認手続きはない
- 2026年11月17日時点の最新版はVPAT 2.5Revで、508、EU、WCAG、INTの四つのEditionがある
- 提出先、調達条件、対象規格に合うEditionを選ぶ
- 製品版、プラン、機能、環境、対象外を固定してから評価する
- 自動検査だけに頼らず、キーボード、拡大、支援技術、主要タスクを確認する
- Conformance Levelは`Supports`、`Partially Supports`、`Does Not Support`、`Not Applicable`を使う
- Remarks and Explanationsには、対象、根拠、既知の例外、利用者影響、回避策を具体的に書く
- 不適合や未修正の課題を隠さず、現在の結果と将来の計画を分ける
- ACRの各判定を社内の試験記録へたどれるようにする
- ACR文書自体もアクセシブルなWord・PDFとして提供する
- 製品変更、修正、依存環境の更新に合わせて再評価し、ACRを更新する
- 発注者は行数を集計せず、自組織の主要タスクに対する影響を確認する

適用法、調達要件、契約上の義務は案件ごとに異なる。実際の提出では、最新のITIテンプレート、募集要項、対象規格を確認し、必要に応じてアクセシビリティ、調達、法務の専門家へ相談する。

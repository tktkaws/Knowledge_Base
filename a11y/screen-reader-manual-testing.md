# スクリーンリーダーでの手動テスト入門 — VoiceOver / NVDA

## なぜスクリーンリーダーテストが必要か

- 自動テストでは、読み上げの自然さ・名前の適切さ・ウィジェット操作感を十分に検証できない
- 「ロールはあるが名前がない」「開閉はできるが状態が伝わらない」などは実機で初めて分かる
- キーボード操作チェックと組み合わせると、支援技術利用時の体験に近い確認ができる

> 参照: [WebAIM — Screen Reader Testing](https://webaim.org/articles/screenreader_testing/)

## 推奨する組み合わせ

| 環境 | スクリーンリーダー | ブラウザ | 備考 |
|---|---|---|---|
| macOS | VoiceOver | Safari | Mac標準。追加インストール不要 |
| Windows | NVDA | Firefox または Chrome | 無料。まずここから始めるとよい |
| Windows（任意） | JAWS | Chrome | 企業・公的機関向けに重要 |
| iOS（任意） | VoiceOver | Safari | ジェスチャー操作。デスクトップとは別対象 |
| Android（任意） | TalkBack | Chrome | モバイル検証用 |

- 最低ライン: **VoiceOver + Safari** と **NVDA + Firefox/Chrome** のどちらか一方、できれば両方
- 同じページでも読み上げが異なることがある — 1種類だけで「完了」にしない

## テスト前の準備

### 心構え

- 最初はマウスを使わず、キーボード（またはモバイルのジェスチャー）だけで操作する
- 「聞こえた情報だけ」でページを理解できるかを基準にする
- 完璧な熟練は不要。基本操作で主要フローを通すことから始める

### 共通で確認すること

1. ページタイトルが読み上げられるか
2. 見出しだけでおよその構造が分かるか
3. リンク・ボタンに名前と役割があるか
4. フォームのラベル・必須・エラーが伝わるか
5. モーダルやアコーディオンなどの状態変化が伝わるか
6. 画像の代替テキストが適切か（装飾は読まれないか）

## VoiceOver（macOS）

### 起動と基本

| 操作 | キー |
|---|---|
| 起動 / 終了 | `Cmd + F5`（Touch ID付きは Touch ID を3回押す場合あり） |
| VOキー | `Ctrl + Option`（以降「VO」と表記） |
| 次 / 前の項目 | `VO + →` / `VO + ←` |
| 実行（クリック相当） | `VO + Space` |
| ローターを開く | `VO + U` |
| 読み上げ停止 | `Ctrl` |

- テスト時のブラウザは **Safari** を使う
- Webコンテンツ内では、VOキー操作で要素単位に進む

### よく使う移動

| 目的 | 操作 |
|---|---|
| 次の見出し | `VO + Cmd + H` |
| 前の見出し | `VO + Cmd + Shift + H` |
| 次のリンク | `VO + Cmd + L` |
| 次のフォームコントロール | `VO + Cmd + J` |
| 次のランドマーク | ローター（`VO + U`）で「ランドマーク」を選択 |
| Tab | フォーカス可能な要素へ通常どおり移動 |

### ローターの使い方

1. `VO + U` でローターを開く
2. `←` / `→` で「見出し」「リンク」「フォームコントロール」「ランドマーク」などを選ぶ
3. `↑` / `↓` で一覧を移動し、`Enter` または `VO + Space` でそこに移動

- 「見出し一覧でページ構造が分かるか」を最初に確認すると効率が良い

### VoiceOverでの確認ポイント

- ボタンが「ボタン」と読まれ、名前があるか
- `aria-expanded` 付きの開閉が「折りたたみ」「展開済み」などと伝わるか
- ダイアログを開いたとき、ダイアログ内にフォーカスが移るか
- 閉じたあと、トリガーにフォーカスが戻るか

> 参照: [Apple — VoiceOver User Guide](https://support.apple.com/guide/voiceover/welcome/mac)

## NVDA（Windows）

### インストールと起動

- [NV Access](https://www.nvaccess.org/) から無料ダウンロード
- 起動後、フォーカスモードとブラウズモードを意識する
- テスト時のブラウザは **Firefox** または **Chrome**

| 操作 | キー（デスクトップ配置） |
|---|---|
| NVDAキー | `Insert`（ノートPC配置では `Caps Lock` の場合あり） |
| 起動後の停止 | `Ctrl` |
| 次 / 前へ1要素 | `↓` / `↑`（ブラウズモード） |
| 要素を有効化 | `Enter` |

### ブラウズモードとフォーカスモード

| モード | 用途 | 切替の目安 |
|---|---|---|
| ブラウズモード | ページを読んで構造移動する | 見出しキー、矢印で読み上げ |
| フォーカスモード | フォーム入力やカスタムウィジェット操作 | 入力欄に入ると自動切替しやすい |

| 操作 | キー |
|---|---|
| フォーカスモードへ | `NVDA + Space` |
| ブラウズモードへ | `NVDA + Space`（トグル） |

- カスタムコンボボックス等でモードが切り替わらない / 戻れない場合は実装側の問題が多い

### よく使う単キー（ブラウズモード）

| キー | 移動先 |
|---|---|
| `H` / `Shift + H` | 次 / 前の見出し |
| `1`〜`6` | そのレベルの見出し |
| `D` / `Shift + D` | 次 / 前のランドマーク |
| `F` / `Shift + F` | 次 / 前のフォームフィールド |
| `K` / `Shift + K` | 次 / 前のリンク |
| `G` / `Shift + G` | 次 / 前のグラフィック |
| `T` / `Shift + T` | 次 / 前のテーブル |
| `B` / `Shift + B` | 次 / 前のボタン |

### 要素リスト

| 操作 | キー |
|---|---|
| 要素リストを開く | `NVDA + F7` |

- リンク一覧・見出し一覧・フォームフィールド一覧をまとめて確認できる
- 「ここをクリック」のような曖昧なリンク名を一覧で見つけやすい

> 参照: [NVDA User Guide](https://www.nvaccess.org/files/nvda/documentation/userGuide.html)

## 初回におすすめのテスト手順

対象ページを1つ決め、次の順で通す。

### 1. ページ読み込み直後

- ページタイトルが読まれるか
- 言語（`lang`）が正しそうか（日本語ページが英語音声になっていないか）

### 2. 構造把握

- 見出し移動（VoiceOver: ローター / `VO + Cmd + H`、NVDA: `H`）
- ランドマーク（ヘッダー・メイン・ナビ・フッター）に到達できるか
- スキップリンクがあれば、最初の Tab で到達しメインへ飛べるか

### 3. インタラクション

- Tab だけで主要操作に到達できるか
- ボタン・リンクの名前と役割が適切か
- フォームでラベルが読まれるか、エラーが伝わるか

### 4. 動的UI

- モーダル: 開閉、フォーカス移動、Escape
- アコーディオン / タブ: 状態（展開・選択）が伝わるか
- トースト / ステータス: ライブリージョンで通知されるか

### 5. コンテンツ

- 意味のある画像に適切な `alt` があるか
- 装飾画像が読み飛ばされるか
- 表があれば、見出しセルとデータの関係が読まれるか

## 記録の取り方

| 項目 | 書くこと |
|---|---|
| 環境 | OS / スクリーンリーダー / ブラウザ / バージョン |
| 手順 | どのキーで何をしたか |
| 期待 | どう読まれるべきか |
| 実際 | 何と読まれたか / 読めなかったか |
| 原因候補 | 名前不足、ロール不足、フォーカス損失など |

```text
環境: macOS / VoiceOver / Safari
手順: VO+U → 見出し → 「お問い合わせ」へ移動 → Tab で送信ボタンへ
期待: 「送信、ボタン」
実際: 「グループ、終了」のみでボタン名が読めない
原因候補: ボタン内テキストがCSSで消えている / aria-label 不足
```

## よくある問題と切り分け

| 症状 | 疑うポイント |
|---|---|
| 何も読まれない / 「グループ」だけ | 名前がない、不適切な `aria-hidden` |
| ボタンなのに「クリック可能」程度 | `role` やネイティブ要素の不足 |
| 開閉が伝わらない | `aria-expanded` 未更新 |
| モーダルを開いても外が読める | `inert` / `aria-modal` / `<dialog>` の不足 |
| 更新に気づかない | `aria-live` 未設定、または要素を後から追加している |
| フォーカスが消える | `display: none` した要素にフォーカスが残っている |
| NVDAで入力できない | フォーカスモードへ入れない / キーをページが奪っている |

## テストのコツ

- 最初から全ページを完璧に聞かない — 主要ユーザーフローを優先する
- 視覚を完全に遮断するのが難しければ、画面を見つつ「読み上げだけ」で判断する練習からでよい
- 速度を少し速め、必要なら音声ログや字幕（対応環境）を併用する
- 実装者自身のテストは有効だが、可能なら支援技術の日常利用者のフィードバックも取る

## 実装チェックリスト（テスター視点）

- [ ] VoiceOver + Safari、または NVDA + Firefox/Chrome で主要フローを通した
- [ ] 見出し・ランドマーク・リンク一覧で構造が把握できる
- [ ] すべての操作可能要素に名前・役割・状態がある
- [ ] フォームのラベルとエラーが読み上げられる
- [ ] 動的な状態変化（開閉・通知・ダイアログ）が伝わる
- [ ] キーボードだけで完遂でき、フォーカスが迷子にならない
- [ ] 再現手順と環境を記録した

## まとめ

- スクリーンリーダーテストは、自動テストでは拾えない「伝わり方」を確認する手動検証
- 入門は VoiceOver（Safari）と NVDA（Firefox/Chrome）の基本操作で十分始められる
- 見出し・ランドマーク・フォーム・動的UIを中心に、主要フローを通す
- 問題は「名前・役割・状態・フォーカス・ライブリージョン」に切り分ける
- 環境と手順を記録し、再現可能なバグ報告にする

> 参照: [WebAIM — Using NVDA to Evaluate Web Accessibility](https://webaim.org/articles/nvda/), [WebAIM — Using VoiceOver to Evaluate Web Accessibility](https://webaim.org/articles/voiceover/)

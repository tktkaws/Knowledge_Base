# WAF（Web Application Firewall）の役割と導入判断の基準

## WAFとは

- WAF（Web Application Firewall）は、Webアプリケーションへの不正なHTTPリクエストを検知・遮断するセキュリティ対策
- 通常のファイアウォールがネットワーク層（IP・ポート）を制御するのに対し、WAFはアプリケーション層（HTTP）を検査する
- SQLインジェクション、XSS、CSRF、パストラバーサルなどのWebアプリケーション攻撃に対する防御層

> 参照: [OWASP — Web Application Firewall](https://owasp.org/www-community/Web_Application_Firewall)

---

## WAFの位置づけ — 多層防御の考え方

```
インターネット
     │
     ↓
┌────────────────┐
│ ファイアウォール  │  ← ネットワーク層: IP・ポートの制御
└────────────────┘
     │
     ↓
┌────────────────┐
│ WAF             │  ← アプリケーション層: HTTPリクエストの検査
└────────────────┘
     │
     ↓
┌────────────────┐
│ Webサーバー      │  ← Nginx / Apache
└────────────────┘
     │
     ↓
┌────────────────┐
│ アプリケーション │  ← Next.js / Express / PHP など
└────────────────┘
     │
     ↓
┌────────────────┐
│ データベース     │  ← MySQL / PostgreSQL など
└────────────────┘
```

- WAFはアプリケーションの前段に配置され、不正なリクエストをアプリケーションに届く前にブロックする
- WAFがあってもアプリケーション側のセキュリティ対策（入力バリデーション、エスケープ等）は必須
- WAFは「多層防御」の1つであり、他の対策の代替にはならない

## WAFが防御できる攻撃

| 攻撃 | WAFでの対策 |
|------|-----------|
| SQLインジェクション | リクエスト内のSQL構文パターンを検知・遮断 |
| XSS | `<script>`タグやイベントハンドラなどのパターンを検知 |
| パストラバーサル | `../`を含むパスを遮断 |
| コマンドインジェクション | シェルコマンドのパターンを検知 |
| HTTPリクエストスマグリング | 不正なHTTPヘッダーを検知 |
| DDoS攻撃（アプリ層） | リクエストレートの制限 |
| 既知の脆弱性攻撃 | CVEに対応したルールで遮断 |
| ボットアクセス | 不正なUser-Agentやアクセスパターンをブロック |

### SQLインジェクションの検知例

```
# 通常のリクエスト（WAFが許可）
GET /users?id=123

# SQLインジェクション攻撃（WAFが遮断）
GET /users?id=123 OR 1=1--
GET /users?id=123; DROP TABLE users;--

WAFのルール:
→ リクエストパラメータにSQL構文（OR、UNION、DROP、--等）が含まれる場合にブロック
```

### XSSの検知例

```
# 通常のリクエスト（WAFが許可）
POST /search
body: query=JavaScript入門

# XSS攻撃（WAFが遮断）
POST /search
body: query=<script>alert('XSS')</script>

WAFのルール:
→ リクエストボディに<script>タグやonerror等のイベントハンドラが含まれる場合にブロック
```

## WAFの種類

### クラウド型WAF

```
インターネット → クラウドWAF → オリジンサーバー
                 (CDNと一体型が多い)
```

| サービス | 提供元 | 特徴 |
|---------|-------|------|
| AWS WAF | Amazon | ALB / CloudFront / API Gatewayと連携 |
| Cloudflare WAF | Cloudflare | CDNと一体。無料プランでも基本的なWAF機能あり |
| Azure Web Application Firewall | Microsoft | Application Gatewayと連携 |
| Google Cloud Armor | Google | Cloud Load Balancingと連携 |

- 導入が簡単（DNS変更やCDN設定だけで利用開始できることが多い）
- マネージドルール（提供元が管理するルールセット）が利用可能
- スケーラビリティに優れる（DDoS対策を兼ねることが多い）
- 通信がクラウドを経由するため、レイテンシがわずかに増加する可能性

### ホスト型（ソフトウェア型）WAF

```
インターネット → Webサーバー + WAFモジュール → アプリケーション
```

| ソフトウェア | 説明 |
|------------|------|
| ModSecurity | Apache / Nginx用のオープンソースWAF |
| NAXSI | Nginx用の軽量WAF |

- サーバーにインストールして使用
- 細かいカスタマイズが可能
- 運用・ルール更新を自前で行う必要がある
- 小規模サイトやコスト重視のケースで検討

### アプライアンス型WAF

- 専用のハードウェアをネットワーク上に設置する方式
- 大規模な企業やデータセンター向け
- 高価だが高性能。フロントエンド開発者が直接関わることは少ない

## WAFの検知方式

### シグネチャベース（パターンマッチング）

- 既知の攻撃パターンをルール（シグネチャ）として定義し、一致するリクエストをブロック
- 最も一般的な方式
- 既知の攻撃には強いが、未知の攻撃（ゼロデイ）は検知できない

```
シグネチャの例:
- リクエストに「UNION SELECT」が含まれる → SQLインジェクション
- リクエストに「<script>」が含まれる → XSS
- リクエストに「../../etc/passwd」が含まれる → パストラバーサル
```

### スコアリングベース

- 複数のルールに部分的にマッチした場合にスコアを加算し、閾値を超えたらブロック
- 1つのルールだけでは判定しないため、誤検知が少ない

```
例:
- パラメータにSQLキーワードあり → +3点
- User-Agentが空 → +2点
- リクエストサイズが異常に大きい → +2点
- 合計7点 ≧ 閾値5点 → ブロック
```

### 振る舞い検知（アノマリベース）

- 正常なリクエストのパターンを学習し、逸脱したリクエストを異常として検知
- 未知の攻撃にも対応できる可能性がある
- 学習期間が必要で、誤検知のチューニングが難しい

## AWS WAFの基本（クラウド型の具体例）

### 構成要素

| 要素 | 説明 |
|------|------|
| Web ACL | ルールを束ねる単位。ALBやCloudFrontに紐づける |
| ルール | 個別の検知条件とアクション（Allow / Block / Count） |
| ルールグループ | 複数のルールをまとめたもの |
| マネージドルールグループ | AWSや第三者が管理するルールセット |

### 主要なマネージドルール

| ルールグループ | 防御対象 |
|--------------|---------|
| AWSManagedRulesCommonRuleSet | OWASP Top 10の基本的な攻撃 |
| AWSManagedRulesSQLiRuleSet | SQLインジェクション |
| AWSManagedRulesKnownBadInputsRuleSet | 既知の脆弱性を狙った入力 |
| AWSManagedRulesBotControlRuleSet | ボットアクセス |
| AWSManagedRulesAmazonIpReputationList | 悪意のあるIPアドレス |

### 導入の流れ

```
1. Web ACLを作成

2. マネージドルールを追加（まずはCountモードで様子見）
   - AWSManagedRulesCommonRuleSet
   - AWSManagedRulesSQLiRuleSet

3. CloudFrontまたはALBに紐づけ

4. ログを確認し、誤検知がないかチェック
   → 正規のリクエストがブロックされていないか

5. 問題なければCountモードからBlockモードに切り替え

6. 必要に応じてカスタムルールを追加
```

```
# 悪い例：いきなりBlockモードで適用 → 正規のリクエストが遮断されるリスク

# 良い例：Countモード（検知のみ、遮断しない）で1〜2週間テストしてから適用
```

## Cloudflare WAFの基本

### 特徴

- CDNとWAFが一体化しているため、導入が簡単（DNSをCloudflareに向けるだけ）
- 無料プランでも基本的なセキュリティ機能（DDoS対策、Bot Fight Mode）が利用可能
- WAFのマネージドルールはPro以上のプランで利用可能

### 基本的な防御機能

| 機能 | プラン | 説明 |
|------|-------|------|
| DDoS防御 | Free | L3/L4/L7のDDoS攻撃を自動緩和 |
| Bot Fight Mode | Free | 明らかなボットをブロック |
| レート制限 | Free（基本） | リクエストレートに基づくブロック |
| WAFマネージドルール | Pro以上 | OWASP ModSecurityルールセット等 |
| カスタムWAFルール | Pro以上 | 独自のルールを定義 |

## WAFの誤検知（False Positive）への対処

### 誤検知とは

- 正規のリクエストがWAFのルールに一致してブロックされること
- 例: CMS（WordPress等）の管理画面でHTML入力 → XSSルールに検知される
- 例: 検索クエリに「SELECT」「FROM」が含まれる → SQLインジェクションルールに検知される

### 誤検知への対処法

```
1. まずCountモードで運用して誤検知を洗い出す

2. ログから誤検知のパターンを特定する
   - どのルールが検知したか
   - どのリクエストパスか
   - どのパラメータが原因か

3. 対処方法を選択する
   a. 特定のパスをWAFの対象から除外
   b. 特定のルールを無効化
   c. ルールのアクションをBlockからCountに変更
   d. 許可リスト（IPアドレス等）を設定

4. 除外設定は最小限にする（過度な除外はセキュリティホールになる）
```

```
# 悪い例：誤検知が出たらルールを丸ごと無効化
→ そのルールが防御する攻撃すべてが通過してしまう

# 良い例：特定のパスやパラメータだけ除外
例: /admin/edit のbodyパラメータだけXSSルールを除外
→ 他のページでは引き続きXSSルールが有効
```

## WAFの導入判断 — 必要か不要か

### WAFが特に有効なケース

| ケース | 理由 |
|--------|------|
| EC・金融など個人情報を扱うサイト | 情報漏洩時の被害が大きい |
| WordPressなどのCMS | 既知の脆弱性が定期的に発見される |
| レガシーアプリケーション | コード修正が困難で、WAFで仮想パッチを当てる |
| PCI DSSなどの準拠が必要 | WAFの導入が要件に含まれる場合がある |
| APIを公開している | 不特定多数からのアクセスを受ける |
| DDoS攻撃のリスクがある | クラウド型WAFはDDoS対策を兼ねることが多い |

### WAFだけでは不十分なケース

| ケース | 理由 |
|--------|------|
| ビジネスロジックの脆弱性 | 認可の不備（他人のデータにアクセスできる等）はWAFでは検知できない |
| 暗号化されたリクエスト | E2Eで暗号化されたペイロードの中身はWAFでは検査できない |
| ゼロデイ攻撃 | シグネチャベースのWAFでは未知の攻撃を検知できない |
| 内部犯行 | WAFは外部からのリクエストを検査するもの |

### 導入コストとのバランス

```
小規模な個人サイト・ブログ:
→ CloudflareのFreeプラン（基本的なDDoS防御 + Bot管理）で十分なことが多い
→ アプリケーション側のセキュリティ対策をしっかり行うことが優先

中規模なWebアプリケーション:
→ Cloudflare Pro / AWS WAFのマネージドルールを検討
→ Countモードで試験運用してから導入

大規模・高セキュリティ要件:
→ クラウド型WAF + カスタムルール + セキュリティ専門チームによる運用
→ ペネトレーションテストと組み合わせる
```

## WAFと他のセキュリティ対策の関係

| 対策 | レイヤー | 守る範囲 |
|------|---------|---------|
| ファイアウォール | ネットワーク層 | IPアドレス・ポートの制御 |
| WAF | アプリケーション層 | HTTPリクエストの検査 |
| 入力バリデーション | アプリケーション | ユーザー入力の形式チェック |
| 出力エスケープ | アプリケーション | XSS防止 |
| パラメータ化クエリ | データベース | SQLインジェクション防止 |
| CSP | ブラウザ | スクリプト実行の制限 |
| HTTPS / HSTS | トランスポート層 | 通信の暗号化・改ざん防止 |

```
# 悪い例：WAFを入れたからアプリケーション側の対策は不要
→ WAFはすべての攻撃を防げるわけではない。バイパス手法も存在する

# 良い例：WAFは多層防御の1つとして導入し、アプリケーション側の対策も併せて行う
→ エスケープ + パラメータ化クエリ + CSP + WAF = 多層防御
```

## WAF運用のベストプラクティス

| 項目 | 内容 |
|------|------|
| Countモードから開始 | 誤検知を確認してからBlockモードに切り替え |
| ログの定期確認 | ブロックされたリクエストを定期的にレビュー |
| ルールの更新 | マネージドルールの更新を追従する |
| 除外設定は最小限 | 過度な除外はセキュリティホールになる |
| アプリケーション対策との併用 | WAFだけに頼らない |
| アラートの設定 | 異常なリクエスト増加を検知できるようにする |
| 定期的な見直し | アプリケーションの変更に合わせてルールを調整 |

---

## まとめ

- WAFはHTTPリクエストを検査し、SQLインジェクション・XSS等のWebアプリケーション攻撃を遮断する
- クラウド型（AWS WAF、Cloudflare）は導入が簡単で、DDoS対策も兼ねる
- Countモードで誤検知を確認してからBlockモードに移行するのが鉄則
- WAFはアプリケーション側のセキュリティ対策（エスケープ、バリデーション等）の代替にはならない
- 多層防御の1つとして位置づけ、コストとリスクのバランスで導入を判断する
- 小規模サイトはCloudflare Freeの基本機能 + アプリケーション対策で十分なことが多い

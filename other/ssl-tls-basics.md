# SSL/TLSとは何か — HTTPSの仕組みと暗号化の基礎

## SSL/TLSとは

- SSL（Secure Sockets Layer）/ TLS（Transport Layer Security）は、インターネット通信を暗号化するプロトコル
- SSLはTLSの前身。現在SSLは非推奨で、実際にはTLSが使われている
- 「SSL証明書」「SSL化」という用語が慣習的に残っているが、技術的にはTLS
- HTTPにTLSを組み合わせたものがHTTPS（HTTP over TLS）

| 用語 | 意味 |
|---|---|
| SSL | TLSの旧名称。SSL 3.0以前は脆弱性があり使用禁止 |
| TLS | SSLの後継プロトコル。現在の標準はTLS 1.2 / 1.3 |
| HTTPS | HTTP + TLS。URLが`https://`で始まる通信 |

- 参照: [RFC 8446 — TLS 1.3](https://datatracker.ietf.org/doc/html/rfc8446)

## バージョンの歴史

| バージョン | 年 | 状態 |
|---|---|---|
| SSL 2.0 | 1995 | 廃止（重大な脆弱性） |
| SSL 3.0 | 1996 | 廃止（POODLE攻撃） |
| TLS 1.0 | 1999 | 非推奨（2020年にブラウザが無効化） |
| TLS 1.1 | 2006 | 非推奨（2020年にブラウザが無効化） |
| TLS 1.2 | 2008 | 現在も広く使用 |
| TLS 1.3 | 2018 | 最新・推奨 |

- TLS 1.0 / 1.1はPCI DSS準拠でも無効化が必須
- 新規構築ではTLS 1.2以上のみを有効にする

- 参照: [RFC 8996 — Deprecating TLS 1.0 and TLS 1.1](https://datatracker.ietf.org/doc/html/rfc8996)

## HTTPSが必要な理由

### HTTPの3つの問題

```
HTTP通信（暗号化なし）:

ブラウザ ──── 平文データ ────→ サーバー
          ↑
        第三者が盗聴・改ざん・なりすまし可能
```

| 脅威 | 内容 | 例 |
|---|---|---|
| 盗聴 | 通信内容が平文で読める | 公衆Wi-Fiでパスワードやクレジットカード番号を傍受 |
| 改ざん | 通信途中でデータを書き換えられる | ISPやプロキシが広告を注入 |
| なりすまし | 偽のサーバーに接続させられる | フィッシングサイトへの誘導 |

### HTTPSが解決すること

```
HTTPS通信（TLSで暗号化）:

ブラウザ ──── 暗号化データ ────→ サーバー
          ↑
        第三者は解読できない
```

| 機能 | 説明 |
|---|---|
| 暗号化（Encryption） | 通信内容を第三者が読めないようにする |
| 認証（Authentication） | 通信相手が本物のサーバーであることを証明する |
| 完全性（Integrity） | 通信途中でデータが改ざんされていないことを保証する |

## TLSの暗号化の仕組み

### 共通鍵暗号と公開鍵暗号

- TLSは2種類の暗号方式を組み合わせて使う

| 暗号方式 | 特徴 | 用途 |
|---|---|---|
| 共通鍵暗号（対称鍵） | 同じ鍵で暗号化・復号。高速 | 実際のデータ通信の暗号化 |
| 公開鍵暗号（非対称鍵） | 公開鍵と秘密鍵のペア。低速 | 鍵交換・認証 |

```
公開鍵暗号:
  公開鍵（誰でも入手可能）→ 暗号化に使用
  秘密鍵（サーバーだけが保持）→ 復号に使用

共通鍵暗号:
  同じ鍵 → 暗号化にも復号にも使用（高速）
```

- 公開鍵暗号は処理が重いため、最初の鍵交換にだけ使う
- 実際のデータ通信は高速な共通鍵暗号で行う

### TLSハンドシェイク（TLS 1.2）

- ブラウザとサーバーがHTTPS通信を開始する際の手順

```
ブラウザ                              サーバー
   │                                    │
   │──── ClientHello ──────────────────→│  対応するTLSバージョン・暗号スイートを通知
   │                                    │
   │←─── ServerHello ──────────────────│  使用するTLSバージョン・暗号スイートを決定
   │←─── Certificate ──────────────────│  SSL証明書（公開鍵含む）を送信
   │←─── ServerHelloDone ─────────────│
   │                                    │
   │──── ClientKeyExchange ───────────→│  プリマスターシークレットを公開鍵で暗号化して送信
   │──── ChangeCipherSpec ────────────→│  以降は暗号化通信に切り替え
   │──── Finished ────────────────────→│
   │                                    │
   │←─── ChangeCipherSpec ─────────────│
   │←─── Finished ─────────────────────│
   │                                    │
   │←──── 暗号化されたHTTP通信 ────────→│  共通鍵で暗号化
```

- ハンドシェイク完了後、両者が同じ共通鍵（セッション鍵）を共有
- 以降のHTTP通信はすべてこの共通鍵で暗号化される

### TLS 1.3の改善点

```
TLS 1.2: 2往復（2-RTT）でハンドシェイク完了
TLS 1.3: 1往復（1-RTT）でハンドシェイク完了。再接続時は0-RTTも可能
```

| 項目 | TLS 1.2 | TLS 1.3 |
|---|---|---|
| ハンドシェイク | 2-RTT | 1-RTT（再接続時0-RTT） |
| 脆弱な暗号スイート | 一部サポート | 完全に廃止 |
| 前方秘匿性 | オプション | 必須（ECDHE） |
| 暗号スイート数 | 約40種 | 5種に限定 |

- TLS 1.3は不要な機能を削除し、セキュリティと速度の両方を改善
- 前方秘匿性（Forward Secrecy）により、秘密鍵が漏洩しても過去の通信は解読不可

- 参照: [Cloudflare — TLSハンドシェイクとは](https://www.cloudflare.com/ja-jp/learning/ssl/what-happens-in-a-tls-handshake/)

## SSL証明書の役割

### SSL証明書とは

- サーバーの公開鍵とドメインの所有者情報を含むデジタル証明書
- 認証局（CA: Certificate Authority）が発行し、サーバーの身元を保証する
- ブラウザはCAの信頼リスト（ルート証明書）を内蔵しており、証明書の正当性を検証する

### 証明書の信頼チェーン

```
ルート証明書（CA）         ← ブラウザに組み込み済み（信頼の起点）
  └─ 中間証明書（中間CA）  ← ルートCAが署名
       └─ サーバー証明書    ← 中間CAが署名（Webサーバーに設置）
```

- ブラウザはサーバー証明書から順にたどり、ルート証明書まで検証する
- 中間証明書が不足していると「証明書エラー」になる

### 証明書に含まれる主な情報

| フィールド | 内容 |
|---|---|
| Subject | 発行先（ドメイン名など） |
| Issuer | 発行元（認証局の名前） |
| Validity | 有効期間（開始日〜終了日） |
| Public Key | サーバーの公開鍵 |
| SAN | Subject Alternative Name（対象ドメインの一覧） |
| Signature | 認証局による電子署名 |

## ブラウザでのHTTPS確認方法

### 安全な接続の表示

```
✓ https://example.com
  └─ アドレスバーに鍵アイコンが表示される
  └─ 証明書の詳細を確認できる（鍵アイコンをクリック）
```

### 安全でない接続の警告

```
✗ http://example.com
  └─ 「保護されていない通信」と表示される

✗ https://example.com（証明書エラー）
  └─ 「この接続ではプライバシーが保護されません」と表示される
  └─ 原因: 証明書の期限切れ、ドメイン不一致、自己署名証明書など
```

## HTTPSが必須となった背景

- **ブラウザの警告強化**: Chrome 68（2018年）以降、すべてのHTTPページに「保護されていない通信」と表示
- **SEOへの影響**: GoogleはHTTPSをランキング要素として採用（2014年〜）
- **HTTP/2の要件**: 主要ブラウザはHTTP/2をHTTPS接続でのみサポート
- **新しいWeb APIの制限**: Service Worker、Geolocation、カメラ/マイクなどはHTTPS必須
- **Cookie属性**: `Secure`属性のCookieはHTTPS接続でのみ送信される

- 参照: [Google — HTTPSをランキングシグナルに使用](https://developers.google.com/search/blog/2014/08/https-as-ranking-signal)

## よくある誤解

### 「HTTPSにすれば完全に安全」

- HTTPSは通信経路の暗号化であり、サーバー自体のセキュリティとは別
- SQLインジェクション、XSS、CSRFなどの脆弱性はHTTPSでは防げない
- HTTPSは「通信の安全」、アプリケーションのセキュリティは別途対策が必要

### 「HTTPSにするとサイトが遅くなる」

- TLS 1.3ではハンドシェイクが1-RTTに短縮され、オーバーヘッドはほぼ無視できる
- HTTP/2（HTTPS必須）はむしろHTTP/1.1より高速
- 現代のハードウェアではTLSの暗号化処理のコストは極めて小さい

### 「個人情報を扱わないサイトはHTTPS不要」

- 通信内容の改ざん防止（広告注入やマルウェア注入）のためにも必要
- ブラウザが「保護されていない通信」と表示するため、ユーザーの信頼に影響
- 新しいWeb APIやHTTP/2を利用するためにもHTTPSが前提

## まとめ

- SSL/TLSはインターネット通信を暗号化するプロトコル。現在の標準はTLS 1.2 / 1.3
- HTTPSはHTTPにTLSを組み合わせたもので、暗号化・認証・完全性を提供
- TLSハンドシェイクで公開鍵暗号を使って共通鍵を交換し、以降は共通鍵で高速に暗号化
- TLS 1.3は1-RTTハンドシェイク、前方秘匿性の必須化など大幅に改善
- SSL証明書は認証局が発行し、サーバーの身元とドメインの所有を保証する
- 現在はすべてのWebサイトでHTTPSが事実上の必須要件

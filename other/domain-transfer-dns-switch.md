# ドメイン移管とDNS切り替えの手順 — ダウンタイムを最小化する方法

## ドメイン移管とDNS切り替えの違い

- 「ドメイン移管」と「DNS切り替え」は混同されやすいが、別の作業

| 作業 | 内容 | 例 |
|---|---|---|
| ドメイン移管（トランスファー） | ドメインの管理元（レジストラ）を変更する | お名前.comからCloudflareに移管 |
| DNS切り替え（ネームサーバー変更） | ドメインのDNS管理先を変更する | レジストラのDNSからRoute 53に変更 |
| DNSレコード変更 | 特定のレコード（Aレコードなど）の値を変更する | サーバー移行でIPアドレスを変更 |

```
ドメイン管理の構造:

レジストラ（ドメインの登録・管理）
  └─ ネームサーバー設定（DNSをどこで管理するか）
       └─ DNSレコード（A, MX, CNAME など）
            └─ 実際のサーバー・サービス
```

- レジストラの変更（移管）とネームサーバーの変更は独立して行える
- サーバー移行時はDNSレコードの変更だけで済む場合が多い

## ドメイン移管（レジストラ間トランスファー）

### 移管の全体フロー

```
移管元レジストラ                          移管先レジストラ
     │                                       │
     │  1. 移管ロック解除                      │
     │  2. 認証コード（Auth Code）取得          │
     │                                       │
     │                    3. 移管申請 ─────────│
     │                    （認証コード入力）      │
     │                                       │
     │  4. 移管承認メール受信                    │
     │  5. 承認（またはタイムアウトで自動承認）    │
     │                                       │
     │                    6. 移管完了 ─────────│
     │                    （5〜7日程度）         │
```

### 移管前の確認事項

| 確認項目 | 説明 |
|---|---|
| ドメインの登録から60日以上経過 | ICANN規定で登録直後の移管は不可 |
| 前回の移管から60日以上経過 | 移管直後の再移管も制限される |
| ドメインの有効期限 | 期限切れ間近のドメインは移管前に更新推奨 |
| 移管ロック（Transfer Lock）の解除 | レジストラの管理画面で解除する |
| Whoisの連絡先メールアドレス | 承認メールが届くアドレスが有効か確認 |
| 認証コード（Auth Code / EPP Code） | 移管元レジストラで取得する |

### 移管手順の詳細

#### 1. 現在のDNS設定を記録する

```bash
# 現在のすべてのレコードを確認・記録
dig example.com ANY
dig example.com A
dig example.com MX
dig example.com TXT
dig example.com NS

# 結果を保存しておく
dig example.com ANY > dns-backup.txt
```

- **移管前に必ず全DNSレコードをバックアップする**
- 移管先のDNSに同じレコードを再設定する必要がある

#### 2. 移管元レジストラでの作業

- ドメインの移管ロック（Transfer Lock / Domain Lock）を解除
- 認証コード（Auth Code / EPP Code / Transfer Key）を取得
- Whois情報のメールアドレスが有効であることを確認

#### 3. 移管先レジストラでの作業

- 移管申請を行い、認証コードを入力
- 支払い手続き（通常1年分の更新料が発生）
- 移管元に承認メールが送信される

#### 4. 移管の承認

- 移管元レジストラまたはWhoisの連絡先に承認メールが届く
- メール内のリンクから承認する
- 承認しない場合、5〜7日後に自動承認される（レジストラによる）

#### 5. 移管完了後の確認

```bash
# ネームサーバーが正しいか確認
dig example.com NS +short

# Whois情報の確認
whois example.com
```

### 注意: `.jp`ドメインの移管

- `.jp`ドメインはICANNの規定ではなくJPRS（日本レジストリサービス）の規定に従う
- 認証コードではなく「指定事業者変更」という手続きで行う
- 移管元と移管先の両方で手続きが必要

## DNS切り替え（ネームサーバー変更）

### ネームサーバー変更が必要な場面

- DNSホスティングサービスの変更（例: レジストラのDNS → Cloudflare）
- CDNサービスの導入（例: Cloudflare経由のプロキシ設定）
- DNS管理を専門サービスに移行したい場合

### ネームサーバー変更の手順

```
1. 新しいDNSサーバーにすべてのレコードを設定
     ↓
2. レコードの内容が正しいことを確認
     ↓
3. TTLを短縮（300秒程度）して反映を待つ
     ↓
4. レジストラでネームサーバーを変更
     ↓
5. 伝播を確認
     ↓
6. 完了後、TTLを通常値に戻す
```

#### 1. 新DNSサーバーにレコードを設定

- 移行先のDNSサーバーに現在と同じレコードをすべて再設定
- **移行前に新DNSサーバーでレコードが正しく応答するか確認**

```bash
# 新しいネームサーバーに直接問い合わせて確認
dig @ns1.new-dns-provider.com example.com A
dig @ns1.new-dns-provider.com example.com MX
dig @ns1.new-dns-provider.com example.com TXT
```

#### 2. TTLを短縮する

- 切り替え前に既存レコードのTTLを短くする（例: 300秒 = 5分）
- TTLの変更が反映されるまで、現在のTTL値の時間（例: 24時間）待つ必要がある

```
# 変更前（TTLが長い）
example.com.  86400  IN  A  93.184.216.34

# 切り替え準備（TTLを短縮）
example.com.  300    IN  A  93.184.216.34
```

- **TTL短縮後、最低でも元のTTL値の時間が経過してから次のステップに進む**
- これにより、古いキャッシュがすべて期限切れになる

#### 3. レジストラでネームサーバーを変更

- レジストラの管理画面でネームサーバーを新しいものに変更
- 通常、変更が全世界に伝播するまで24〜48時間かかる

```
# 変更前
example.com  NS  ns1.old-provider.com
example.com  NS  ns2.old-provider.com

# 変更後
example.com  NS  ns1.new-provider.com
example.com  NS  ns2.new-provider.com
```

#### 4. 伝播の確認

```bash
# 各地域のDNSサーバーからの応答を確認
dig @8.8.8.8 example.com NS +short       # Google DNS
dig @1.1.1.1 example.com NS +short       # Cloudflare DNS
dig @208.67.222.222 example.com NS +short # OpenDNS

# 名前解決の全経路を確認
dig +trace example.com
```

- オンラインツール（[whatsmydns.net](https://www.whatsmydns.net/)など）で世界各地の伝播状況を確認できる

## サーバー移行時のDNS切り替え

### Webサーバーの移行

- 最もよくあるケース：ホスティングサーバーの変更に伴うAレコードの変更

```
切り替え手順:

1. 新サーバーにサイトを構築・動作確認
2. TTLを短縮（300秒）→ 元のTTL時間分待つ
3. AレコードのIPアドレスを新サーバーに変更
4. 伝播を確認
5. 旧サーバーは1〜2週間残しておく
6. TTLを通常値に戻す
```

```
# 変更前
example.com.      300  IN  A  198.51.100.10   ← 旧サーバー
www.example.com.  300  IN  CNAME  example.com.

# 変更後
example.com.      300  IN  A  203.0.113.20    ← 新サーバー
www.example.com.  300  IN  CNAME  example.com.
```

### hostsファイルでの事前確認

- DNS変更前に、新サーバーでサイトが正しく動作するか確認する方法

```bash
# /etc/hosts に追記（macOS / Linux）
# C:\Windows\System32\drivers\etc\hosts（Windows）

203.0.113.20  example.com
203.0.113.20  www.example.com
```

- hostsファイルに設定すると、自分のPCだけが新サーバーに接続する
- ブラウザで表示・動作確認後、問題なければDNSを切り替える
- **確認後はhostsファイルの追記を必ず削除する**

### メールサーバーの移行

- メールサーバーの移行はWebサーバーよりも慎重に行う必要がある
- 移行期間中にメールが旧サーバーと新サーバーに分散して届く可能性がある

```
メールサーバー移行の手順:

1. 新メールサーバーの設定完了・テスト
2. 新サーバーでメール受信できることを確認
3. TTLを短縮（300秒）→ 元のTTL時間分待つ
4. MXレコードを新サーバーに変更
5. SPF / DKIM / DMARCレコードも更新
6. 旧サーバーでの受信メールを定期確認（1〜2週間）
7. TTLを通常値に戻す
```

```
# 変更前（旧メールサーバー）
example.com.  300  IN  MX   10  mail.old-server.com.
example.com.  300  IN  TXT  "v=spf1 ip4:198.51.100.10 ~all"

# 変更後（Google Workspace）
example.com.  300  IN  MX   1   ASPMX.L.GOOGLE.COM.
example.com.  300  IN  MX   5   ALT1.ASPMX.L.GOOGLE.COM.
example.com.  300  IN  TXT  "v=spf1 include:_spf.google.com ~all"
```

- 移行期間中は旧サーバーと新サーバーの両方でメール受信設定を有効にしておく
- SPFレコードには旧サーバーと新サーバーの両方を含めておく

```
# 移行期間中のSPF（両方を含める）
example.com.  300  IN  TXT  "v=spf1 ip4:198.51.100.10 include:_spf.google.com ~all"
```

## ダウンタイムを最小化するためのベストプラクティス

### 事前準備チェックリスト

| ステップ | 内容 | タイミング |
|---|---|---|
| 1 | 現在のDNSレコードを完全にバックアップ | 作業の1週間前 |
| 2 | 新環境の構築・動作確認を完了 | 作業の数日前 |
| 3 | TTLを300秒に短縮 | 作業の24〜48時間前（現TTL値分の時間前） |
| 4 | TTL短縮の反映を確認 | 切り替え直前 |
| 5 | DNS切り替えを実行 | 計画したタイミング |
| 6 | 伝播状況を監視 | 切り替え後24〜48時間 |
| 7 | 旧環境を一定期間維持 | 切り替え後1〜2週間 |
| 8 | TTLを通常値に戻す | 完全移行確認後 |

### よくある失敗と対策

#### TTLを短縮せずに切り替えた

```
問題:
  TTL 86400（24時間）のまま切り替え
  → 最大24時間、旧IPがキャッシュに残る
  → その間は旧サーバーにアクセスが向く

対策:
  切り替え前にTTLを300秒に短縮し、
  元のTTL値の時間が経過してから切り替える
```

#### 新DNSサーバーにレコードを設定し忘れた

```
問題:
  ネームサーバーを変更したが、新DNSにMXレコードを設定していなかった
  → メールが届かなくなる

対策:
  切り替え前に新DNSサーバーへの直接問い合わせで全レコードを確認
  dig @new-ns.example.com example.com MX
```

#### 旧サーバーを即座に停止した

```
問題:
  DNS切り替え直後に旧サーバーを停止
  → キャッシュで旧IPに向くユーザーがアクセス不能

対策:
  旧サーバーは最低1〜2週間は稼働させておく
  旧サーバーから新サーバーへのリダイレクト設定も有効
```

### 切り替え作業のタイミング

- アクセスの少ない時間帯（深夜・早朝）に実施
- 週末や祝日の前日は避ける（問題発生時の対応が遅れる）
- 関係者（クライアント、チームメンバー）に事前告知

## トラブルシューティング

### DNS切り替え後にサイトが表示されない

```bash
# 1. DNSの伝播状況を確認
dig example.com A +short
dig @8.8.8.8 example.com A +short

# 2. 新旧どちらのIPが返ってきているか確認
# 旧IPが返る場合 → キャッシュが残っている。TTLの時間分待つ

# 3. 新サーバーが正しく応答するか確認
curl -I --resolve example.com:443:203.0.113.20 https://example.com

# 4. ローカルのDNSキャッシュをクリア
# macOS
sudo dscacheutil -flushcache && sudo killall -HUP mDNSResponder
# Windows
ipconfig /flushdns
```

### メールが届かない

```bash
# 1. MXレコードの確認
dig example.com MX +short

# 2. SPFレコードの確認
dig example.com TXT +short | grep spf

# 3. 新メールサーバーへの接続テスト
telnet mail-server.example.com 25

# 4. メールヘッダで経路を確認
# 届いたメールのヘッダ「Received:」行を確認
```

### SSL証明書エラーが出る

```
原因:
  新サーバーにSSL証明書が設定されていない、
  またはドメイン名と証明書の不一致

対策:
  1. 新サーバーでSSL証明書を事前に取得・設定
  2. Let's EncryptはDNS-01チャレンジで事前取得可能
  3. DNS切り替え後にHTTP-01チャレンジで再取得
```

```bash
# DNS-01チャレンジで事前にSSL証明書を取得（certbot）
sudo certbot certonly --manual --preferred-challenges dns -d example.com
# → TXTレコードの追加を求められる
# → _acme-challenge.example.com に指定値を設定
```

## まとめ

- ドメイン移管（レジストラ変更）とDNS切り替え（ネームサーバー変更）は別の作業
- 移管前には全DNSレコードのバックアップ、認証コードの取得、移管ロックの解除が必要
- DNS切り替え前にTTLを短縮（300秒）し、元のTTL時間分を待ってから実行する
- 新DNSサーバーへの直接問い合わせで、レコードが正しく応答するか事前確認する
- メールサーバー移行時はSPF/DKIM/DMARCの更新と、旧サーバーの並行運用が重要
- 旧サーバーは切り替え後1〜2週間は維持し、完全移行を確認してから停止する
